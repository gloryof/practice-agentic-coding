# ADR-0001: React Router SPAをフロントエンドの初期アーキテクチャに採用する

## ステータス
置換済み

2026-07-26 に [ADR-0002](0002-adopt-nextjs-bff-architecture.md) で置き換えた。

## 決定日
2026-07-21

## 背景
図書館利用者向けフロントエンドでは、登録、ログイン、蔵書検索、在庫確認、予約を実現する。検索、在庫確認、予約は認証後の対話的な操作であり、現在はログイン不要の公開書誌ページ、SEO、デプロイ、実利用者データの要件がない。

API はローカルで独立して動作する Spring Boot アプリケーションである。フロントエンドはこの境界を維持し、現在の小規模な単一館向け構成に対して、実行時サーバーと外部サービスを不要にする必要がある。一方、将来公開ページが必要になった場合に SSR または静的生成へ変更できる経路は残す。

また、実際のデプロイ設計を練習できるよう、フロントエンド成果物は一度ビルドした同一資産を環境間で移送可能とし、公開可能な環境差分を実行時に注入できる必要がある。

## 決定
- React、React Router Framework Mode、Vite、TypeScript strict を採用する。
- React Router は `ssr: false` の SPA Mode とし、実行時の描画をブラウザで行う。
- Node.js 24 LTS と npm を使用し、`package-lock.json` で依存解決を固定する。
- 対象ブラウザは Vite の `baseline-widely-available` とする。
- ルートは `app/routes.ts` へ明示し、機能単位の構成と薄いルート層を採用する。
- HTTP 通信はブラウザ標準の `fetch` を共通境界から使用する。
- `/config/app-config.json` を起動前に取得し、公開可能な実行時設定を検証してからアプリケーションを起動する。
- ローカルでは Vite 開発プロキシから別起動の Spring Boot API へ接続する。
- ビルド成果物は API から独立した静的資産とし、Spring Boot JARへ同梱しない。
- Node.js は開発とビルドに使用し、静的配信だけを目的とする本番 Node.js サーバーを必須にしない。
- 依存関係は手動で更新し、外部テレメトリは初期構成へ含めない。

現在有効な詳細規則は `frontend/docs/frontend-guidelines.md` を正本とする。

## 比較した選択肢

### レンダリングとReact構成
| 候補 | メリット | デメリット | 判断 |
|---|---|---|---|
| React Router Framework ModeのSPA Mode | CSRの静的配信を維持しつつ、型付きルート、コード分割、将来のルート単位SSRへの経路を持てる | ビルド時にルートを描画するため、初期描画をブラウザAPIから分離する必要がある | 採用 |
| Vite + React Router Data Mode | 純粋なブラウザSPAとして構成を直接制御できる | コード分割やデータ取得規則を独自に決め、SSR移行時の変更が増える | 不採用 |
| Next.js Static Export | 静的出力からNext.jsのサーバー機能へ拡張できる | 既存Spring Boot APIだけを使用する現在構成に対してNext.js固有の概念が増える | 不採用 |
| 純粋なSSR | JavaScript依存を抑え、初期HTMLをリクエストごとに生成できる | 常駐サーバー、認証伝播、キャッシュ、障害領域が増え、現在の認証中心フローで利点が小さい | 不採用 |

### HTTP通信
| 候補 | メリット | デメリット | 判断 |
|---|---|---|---|
| ブラウザ標準の`fetch` | 追加依存がなく、`AbortSignal`を使える | HTTPエラー判定、解析、タイムアウト、共通エラー化を実装する必要がある | 採用 |
| Axios | interceptor、timeout、エラー処理などがまとまっている | 追加依存と独自エラー型を持ち、近年の脆弱性対応も継続して必要になる | 不採用 |

### 設定注入
| 候補 | メリット | デメリット | 判断 |
|---|---|---|---|
| 起動時に設定JSONを取得 | 同一ビルド成果物を環境間で移送でき、ConfigMap、起動時生成、静的配信へ同じ契約を適用できる | 初期取得、実行時検証、取得失敗、キャッシュを扱う必要がある | 採用 |
| Viteのビルド時環境変数 | Vite標準だけで単純に構成できる | 環境ごとに再ビルドが必要で、同一成果物の昇格ができない | 不採用 |
| HTMLへの設定注入 | 追加リクエストがない | 安全なエスケープ、HTML書き換え、キャッシュ管理が必要になる | 不採用 |

### 配布単位
| 候補 | メリット | デメリット | 判断 |
|---|---|---|---|
| 独立した静的成果物 | フロントエンドとAPIを独立してビルド、配布、差し戻しできる | デプロイ時は配信元、API互換性、リリース順序を設計する必要がある | 採用 |
| Spring Bootへ同梱 | 単一プロセスと同一Originで配信できる | フロント変更とAPIのビルド・リリース・ロールバックが結合する | 不採用 |
| Node.jsサーバーで静的配信 | 将来SSR/BFFの実行環境を先に用意できる | 現在は静的配信だけのためにランタイム、監視、依存更新を増やす | 不採用 |

## 影響
- フロントエンドとAPIの所有境界、障害箇所、ビルド成果物を分離できる。
- CSR実行時にNode.jsサーバーの計算・監視コストは発生しない。
- SPAのすべてのURLをエントリHTMLへ戻す静的配信設定が必要になる。
- 実行時設定の取得と検証はアプリケーション起動の新しい障害点になるため、利用者が識別できる設定エラーを表示する必要がある。
- ローカル障害調査では、ブラウザ、Vite開発プロキシ、Spring Boot APIを独立した障害境界として扱える。
- SSRへ変更する場合も、認証済みデータ取得、CookieまたはBFF、サーバー運用を新たに設計する必要がある。
- 手動依存更新では脆弱性検知が自動化されないため、新規依存追加時と機能着手時の確認を必須とする。

## 再評価条件
- ログイン不要の公開ページ、SEO、OGPまたは初期HTML要件が具体化した場合、SSRまたは静的生成を再評価する。
- デプロイする場合、静的ホスティング、同一Origin化、リリース順序、ロールバック、設定配信を決定する。
- 実利用者データを扱う場合、依存関係の自動更新、継続的な脆弱性検査、外部テレメトリを再評価する。
- BFFを必要とする認証またはAPI集約要件が確定した場合、Node.jsサーバー境界を再評価する。

## 後続決定
- API型同期、認証、CORS、APIエラー、相関識別子はフロントエンドAPI・認証連携タスクで決定する。
- 状態所有と非同期イベントはフロントエンド状態・イベント管理タスクで決定する。
- UIとアクセシビリティはフロントエンドデザインシステムタスクで決定する。
- テスト、CI、画面性能、ブラウザE2Eはフロントエンド品質・非機能要件タスクで決定する。
