# Server Actionの設計単位を標準化する

## ステータス
- Status: Proposed
- Updated: 2026-08-16 - 起票

## 背景
Next.jsのServer Actionは、APIエンドポイントのようにURLで処理単位が明示されず、同じ画面やURLから複数のActionを呼び出せる。
一方、Actionをどの粒度で分割・共有するかはフレームワークによって一意に決まらないため、実装者ごとに設計判断がずれる可能性がある。

現在のログインと利用登録では、明確な利用者操作ごとにServer Actionを定義し、画面とSpring APIを接続するBFFの入口として利用している。
今後、検索、予約、取消、プロフィール更新などの操作が増える前に、この実装方針を再利用可能な規則として明文化する必要がある。

## 影響
設計単位が曖昧なままでは、複数の操作を`actionType`などで振り分ける巨大なAction、入力項目単位に細分化されたAction、画面ごとに重複するActionが混在する可能性がある。
その結果、入力検証、認証・認可、エラー状態、テスト、ログの責務が不明瞭になり、障害調査や仕様変更の影響範囲も把握しにくくなる。

反対に、画面単位だけで機械的に分割すると、同じ意味を持つ操作を複数画面から実行する場合にもActionが重複し、振る舞いが分岐する可能性がある。

## 対応案
- `frontend/docs/frontend-guidelines.md`にServer Actionの設計単位と責務を追加する。
- 原則として、1つのServer Actionを、利用者が意図して実行する1つの操作または1つのフォーム送信に対応させる。
- Server Actionを画面やURLではなく操作の意味で命名し、`loginAction`、`registerAction`、`cancelReservationAction`のように目的を識別できる名前とする。
- 複数の異なる操作を汎用的な`actionType`で振り分ける巨大なActionと、1つの業務操作を入力項目単位に分割する過度に細かいActionを避ける。
- 操作の意味、入力、認証・認可、成功時の結果、失敗時の扱いが同じ場合に限り、複数画面やコンポーネントからActionを共有できることを明記する。
- Server Actionの責務を、入力の取得と検証、BFF内のAPIクライアント呼び出し、画面用状態への変換、リダイレクトまたはキャッシュ更新の制御に限定する。
- 業務ルールと永続化をSpring API側へ置き、Server Actionへ業務ロジックを重複実装しない。
- Server Actionと外部公開APIを区別し、URL、HTTPメソッド、安定した通信契約が必要な呼び出しをServer Actionで代替しない。
- すべてのActionを独立したサーバー入口として扱い、入力検証と必要な認証・認可をActionごとに省略しない。
- 同じURLに複数のActionが存在しても運用時に処理を特定できるよう、ログへ安定した操作名とrequest IDを記録する方針を定める。
- ログイン、利用登録、および今後追加する検索・予約機能を例に、規則の適用可否を確認する。

## 確認方法
- 新規のServer Actionについて、対応する利用者操作、入力、成功結果、失敗結果を一意に説明できる。
- 1画面に複数の操作がある場合も、各Actionの境界を規則から判断できる。
- 同じ操作を複数画面から利用する場合に、Actionを共有できる条件を規則から判断できる。
- Server Action、BFF内のAPIクライアント、Spring APIの責務を既存のログイン・利用登録実装へ矛盾なく適用できる。
- 汎用Actionへの過剰な集約と、入力項目単位への過剰な分割をレビューで検出できる。
- 複数のActionが同じURLへPOSTされた場合も、サーバーログから実行された操作を識別できる。
- 文書更新後に`./scripts/check-no-local-paths.sh`を実行する。
