# Agentワークフローの選択結果を回帰テストする

## ステータス
- Status: Proposed
- Updated: 2026-08-16 - 起票

## 背景
コンテキスト選択、タスク規模分類、ワークフロー選択、レビュー選択を条件付きにすると、不要な参照を減らせる一方、ルーティング規則の変更によって必要な文書やレビュアーを誤って除外する可能性がある。現状は代表例を人間が文書上で確認する方法が中心で、選択結果の回帰を継続的に検知する成果物がない。

## 影響
選択規則の変更が静かに品質ゲートを迂回すると、認証・認可、DB、API契約、ユーザー向け振る舞いなどの高リスク変更で必要なレビューや規則が適用されない。毎回Agentの長い実行ログを人手で比較する方法は継続しにくい。

## 対応案
- 代表依頼と変更対象を入力し、期待する対象領域、規模、コンテキスト、ワークフロー、レビュアー、検証を宣言できる回帰ケース形式を定義する。
- 少なくとも、Controller名変更、テストだけの変更、予約テーブル列追加、認可規則変更、フロントエンド文言修正、BFF認証変更、APIと画面の横断変更をケース化する。
- 各ケースで`expected`だけでなく、読み込むべきでない文書や起動すべきでないレビュアーを`not expected`として検証できるようにする。
- 判定ロジックを機械実行可能な形にできる場合は自動テストを追加する。文書とAgent判断に残る部分は、固定入力に対する構造化結果の評価手順を用意する。
- 必須コンテキストやレビューの欠落を、不要な追加より高い重大度で失敗させる。
- 選択規則、索引、フローを変更する際に回帰ケースを実行する入口と、失敗時にどの条件が変わったか分かる出力を用意する。
- トークン量の測定はこのTODOへ混在させず、選択の正しさと再現性を対象にする。

## 確認方法
- 代表ケースで期待するコンテキスト、ワークフロー、レビュアー、検証が一致する。
- 必須のセキュリティまたはDBレビューを意図的に除外すると回帰検査が失敗する。
- 無関係なテーブル規則やセキュリティレビューを意図的に追加した場合も差分を検知できる。
- 同じ入力を繰り返したときに、比較可能な構造化結果が得られる。
- 既存の実装フローとレビュースキルの固定出力契約を壊さない。
- 文書変更後に`./scripts/check-no-local-paths.sh`が成功する。
