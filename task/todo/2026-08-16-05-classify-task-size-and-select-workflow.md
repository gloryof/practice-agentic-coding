# タスク規模に応じてワークフローとレビューを選択する

## ステータス
- Status: Proposed
- Updated: 2026-08-16 - 起票

## 背景
現行の`agents/flows/implementation-task-flow.md`は対象領域を4分類し、領域別フローは変更の焦点からレビュアーを選択している。一方、文言修正や局所的な設定変更と、複数境界を変更する高リスク実装を、規模と影響度で区別する共通分類はない。

対象領域分類だけでは、軽微な変更にも領域別の標準実行順序や広い検証が適用される一方、複雑な変更に追加設計や複数レビューが必要かを一貫して説明しにくい。

## 影響
軽微な変更へ過剰な探索、設計、レビュー、検証を適用すると処理時間とコンテキストが増える。複雑な変更を軽く扱うと、仕様、境界、セキュリティ、DB、テストへの影響を見落とす。

## 対応案
- 既存の対象領域分類と変更焦点分類を置き換えず、その前後で再利用できる`trivial`、`normal`、`complex`の規模・影響分類を定義する。
- 分類条件を、変更ファイル数だけでなく、ユーザー向け振る舞い、契約、境界、認証・認可、DB、依存関係、運用、移行、検証範囲への影響で判定する。
- `trivial`は局所編集と最小検証、`normal`はコンテキスト選択・実装・変更条件に対応する検証とレビュー、`complex`は仕様またはドメイン確認・設計・複数レビュー・横断検証を基本経路とする。
- 既存の`product_design_focus`、`architecture_design_focus`、`security_focus`、`database_change_focus`、`test_quality_focus`をレビュー選択の正本として再利用し、同じ条件を別表へ複製しない。
- コンテキスト選択結果をレビュー選択へ渡し、レビュアー要否を判定するための追加文書読み込みを避ける。
- 実装後の差分が初期分類を超えた場合は上位分類へ昇格し、必要なレビューと検証を追加する。下位分類への自動降格は行わず、理由を記録する。
- `repository_shared_implementation`に含まれる文書・プロセス改善との境界を明確にし、保留中の`task/todo/deferred/2026-07-18-04-add-default-task-routing.md`を無条件に再開しない。

## 確認方法
- typo、局所的なテスト修正、通常の機能追加、DB列追加、認可変更、APIと画面の横断変更が期待する規模へ分類される。
- 各例で必要な工程、検証、レビュアーと省略理由が一意に決まる。
- 軽微な変更でドメイン分析や無関係なレビューが実行されない。
- 複雑な変更で必要な仕様確認、設計、レビュー、横断検証が省略されない。
- 実装後に影響が拡大した例で分類が昇格し、選択結果が更新される。
- 文書変更後に`./scripts/check-no-local-paths.sh`が成功する。
