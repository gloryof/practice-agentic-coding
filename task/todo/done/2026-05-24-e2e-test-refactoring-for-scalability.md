# E2Eテストの拡張性を考慮したリファクタリング

## ステータス
- Status: Done
- Updated: 2026-05-24 - 起票
- Updated: 2026-06-07 - E2Eを共通化してシナリオ分割を実施

## 背景
- 現状のE2Eテストは実質1テストケースを前提とした構成で、シナリオ追加時の再利用性が低い。
- 今後APIエンドポイントやユースケースが増えると、重複コードや前提条件の散在によりメンテナンス負荷が増大する。

## 影響
- API追加のたびにテストコード変更範囲が広がり、修正コストとレビューコストが上がる。
- 共通セットアップや検証ロジックの重複により、変更漏れ・不整合が発生しやすくなる。
- テスト失敗時の原因切り分けが難しくなり、CIの調査時間が増える。

## 対応案
- E2Eテストの共通処理（認証、データ準備、リクエスト実行、レスポンス検証）をヘルパー/Fixture層へ分離する。
- API単位またはユースケース単位でテストクラスを分割し、責務を明確化する。
- シナリオ追加時に最小差分で記述できるテストテンプレート（命名規約・記述パターン）を定義する。
- 将来のケース増加を見据え、テストデータ生成と後片付けの標準手順を整理する。

## 確認方法
- 既存1ケースを新構成へ移行し、同等の検証結果が得られることを確認する。
- 追加想定のダミーAPIシナリオを1件分作成し、重複実装を増やさずに記述できることを確認する。
- CI実行時間と失敗時ログの可読性を確認し、現状より悪化しないことを確認する。
