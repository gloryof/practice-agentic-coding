# 検査用環境の起動・終了とZAP検査を整備する

開発環境に触れずに検査用環境を起動し、BFFと業務APIへの動的検査を実行できるようにする。

## 背景

API・BFFはローカルで起動し、DB・Redis・ZAPはComposeで実行する方針を決定した。  
開発用とポートを共用し、データと所有資源を分離する。

## 課題

検査用環境と認証済みZAP検査を、安全に再実行できる必要があった。

ランナーは省略時と`--env dev`で従来の開発用操作を選択する。  
`start/stop --env security`で専用環境を管理し、不正な引数はDBを操作する前に拒否する。  
専用環境の起動・停止、所有資源管理、ZAPの実装と実機検証を完了した。

アプリ固有シナリオの接続と補完は子タスク05で行う。  
04の完了後も、それまでの`dynamic`全体はシナリオ未実装として終了コード`2`を維持する。

## 完了条件

- 開発環境を変更せずに検査環境を起動・停止できる。
- ポート使用中は環境作成・DB初期化前に終了する。
- 失敗・中断時も当該実行の所有資源だけを片付ける。
- BFFと業務APIを未認証・認証済みの双方で検査できる。
- 認証失敗と検査未完了を成功と扱わない。
- 既存の認証・Origin検証を維持する。
- dynamicグループと個別スクリプトから検査できる。

## 対応結果

- 開発用Composeを呼ばず、検査専用DB・RedisとローカルAPI・BFFを起動するランナーを追加した。
- BFFは検査用コピーでビルドし、開発用の環境設定と`.next`を変更しない。
- IPv4・IPv6のポート確認、排他制御、リスナーPID照合、実行IDによる所有資源の片付けを追加した。
- ZAPの版・digest・主要アドオンを固定し、4区分の受動・能動検査と認証維持を実装した。
- 登録・ログイン・認証済み検索・予約への到達、不正Originの拒否を実機で確認した。
- 最終の4区分は220.6秒で完走し、指摘ありの終了コード`1`になった。
- dynamic全体は、子タスク05で接続するシナリオが未実装のため`2`を維持する。
- 正常終了後にAPI・BFFのリスナー、検査コンテナ・DBボリューム・ネットワーク、管理情報が残らないことを確認した。
- 起動失敗・停止の実機確認と、ポート競合・中断・所有権不一致・時間切れ・認証失敗・未完了判定の回帰確認を実施した。
- ランナーと検査処理の単体テスト28件、API品質ゲート、Compose構成、文書検査が成功した。
- 指摘候補とNext.jsの更新推奨は[05: 初回全体確認](2026-10-11-05-run-initial-security-review.md)へ引き継いだ。

実行コマンドと制約は[セキュリティ検査の実行方法](../../../docs/security/security-checks.md)を参照する。

## 実装方法案

以下の構成と動作を実装する。

- API起動スキルのランナーへ`start/stop --env security`を追加する。
- `--env dev`と省略時の既存動作を維持する。
- 検査用ComposeプロジェクトでDB・Redisを起動し、migrationとseedを適用する。
- ZAPで検査用ユーザーを登録し、BFFはCookie、APIはBearerで認証する。
- 接続設定の調整が複雑ならAPI・BFFのコンテナ化を検討する。
- 最小限のアドオンと安定版標準ルールを使用する。
- 準備・ビルドを除く動的検査を最大30分、同時リクエスト数を1とする。
- 時間上限到達を終了コード`2`として扱う。
- ブラウザ固有の確認は既存Playwright E2Eを活用する。
- [既存環境を停止し得る性能検査の事案](../2026-10-25-02-protect-existing-api-during-frontend-performance-check.md)を確認し、危険な終了処理を流用しない。
