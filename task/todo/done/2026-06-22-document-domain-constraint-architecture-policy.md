# ドメイン制約のアーキテクチャ方針を記載する

## ステータス
- Status: Done
- Updated: 2026-06-22 - 起票
- Updated: 2026-07-11 - ドメイン制約の責務、配置、依存方向、違反理由の型付けと仕様からの探索規約を整備し、予約可能条件の実装を新方針へ移行

## 背景
`product/domain-context` では、複数の状態やモデルを組み合わせて業務上の可否を判定する概念をドメイン制約として定義している。一方、`api/docs/architecture.md` のドメイン分類には `model`、`event`、`service`、`repository` の方針しかなく、ドメイン制約を実装する際の責務、配置、依存方向が定義されていない。

## 影響
ドメイン制約の実装方針がないまま機能開発を進めると、同じ性質の判定がドメインモデル、ドメインサービス、ユースケースへ分散し、パッケージ構成やエラー表現が機能ごとに不統一になる。これにより、仕様上のドメイン制約と実装の対応関係が不明確になり、業務ルールの変更やテストが難しくなる。

## 対応案
- `api/docs/architecture.md` に、ドメイン制約の定義と責務を追加する。
- ドメイン制約と、単一モデルの不変条件、ドメインサービス、ユースケースの判定責務との境界を定義する。
- ドメイン制約のパッケージ配置、命名、依存可能な要素を定義する。
- 判定結果と複数の違反理由を表現する方法、および業務エラーとの対応方針を定義する。
- `product/domain-context/*/domain/constraint` の仕様から実装を探索できる対応規約を定義する。
- 必要に応じて `api/AGENTS.md` のドメインパッケージ分類にドメイン制約を追加する。

## 確認方法
- `api/docs/architecture.md` だけで、ドメイン制約をどのレイヤーとパッケージへ配置し、何に依存させるか判断できることを確認する。
- 予約可能条件を例に、予約者と予約対象書誌を使った判定および複数の違反理由を、規約に従って一意に設計できることを確認する。
- `api/AGENTS.md` と `api/docs/architecture.md` のドメイン分類に矛盾がないことを確認する。

## 期限 / 優先度
- 期限: 予約可能条件のAPI実装着手前
- 優先度: High
