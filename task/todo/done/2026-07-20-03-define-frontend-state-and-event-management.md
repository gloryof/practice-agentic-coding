# フロントエンドの状態・イベント管理方針を定義する

## ステータス
- Status: Done
- Updated: 2026-07-26 - Next.js標準機能による状態所有、イベント、非同期競合、二重送信、エラー回復、テスト配置を決定
- Updated: 2026-07-20 - 起票

## 背景
フロントエンドでは認証、検索条件、API取得結果、フォーム、画面表示など複数の状態とイベントを扱うが、その所有境界と更新規則が未定義である。

## 影響
管理方法が画面ごとに分かれると、状態の不整合、不要な再描画、イベント処理漏れ、検索や予約の二重実行、保守困難なイベント連鎖が発生しやすい。

## 対応案
- 認証状態、URL状態、フォーム状態、APIサーバー状態、ローカルUI状態を分類し、所有者とライフサイクルを決定する。
- コンポーネント間通知、画面横断通知、イベントハンドラーの配置と命名の規則を決定する。
- 非同期処理のキャンセル、競合、古いレスポンス、二重送信、ローディング、エラー回復の扱いを決定する。
- 状態管理ライブラリや汎用イベントバスは、フレームワーク標準機能で不足する根拠がある場合のみ候補とする。
- 決定内容をフロントエンド開発ガイドへ記載する。

## 決定内容
- 認証、URL、フォーム、APIサーバー、ローカルUI、派生状態の正本、所有者、更新方法、破棄タイミングを分類した。
- 認証状態はBFFセッションとSpring Boot API、検索条件は明示送信後のURL、API取得結果はサーバー描画を正本とし、Client Stateへ複製しない。
- フォームはネイティブ機能、`useActionState`、`useFormStatus`を使用し、状態管理、クライアントデータキャッシュ、フォーム管理の外部ライブラリを初期導入しない。
- コンポーネント間通知はpropsと最小共通親、画面横断通知はURL、サーバー状態、再検証、リダイレクトで扱い、汎用イベントバスを使用しない。
- 検索はApp Routerの中断可能なGETナビゲーションで最新URLに対応する結果だけを表示し、例外的なクライアント取得ではキャンセルと古い応答の破棄を併用する。
- 更新操作は操作単位のpendingとsingle-flightで同一UIからの並行実行を抑止し、APIの認証、認可、業務制約、トランザクションを最終防御とする。
- 予約成立などの更新結果を楽観表示または自動再試行せず、サーバー成功後の確定結果を表示する。
- 単体・コンポーネントテストを機能の近くへ、ルーティングと競合を含むテストを`frontend/e2e`へ配置する方針を決定した。
- 詳細は`frontend/docs/state-and-event-management.md`、入口は`frontend/docs/frontend-guidelines.md`を正本とする。

## 確認方法
- ログイン状態変更、検索条件変更と連続実行、予約ボタン連打を例に、状態とイベントの流れを説明できることを確認する。
- 各状態の正本、更新主体、破棄タイミングが一意であることを確認する。
- 競合や二重実行を再現する自動テストの配置方針が決まっていることを確認する。
