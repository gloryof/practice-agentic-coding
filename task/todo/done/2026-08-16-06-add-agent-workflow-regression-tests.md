## 終了判断
`agents/benchmarks/README.md`と`agents/benchmarks/RESULT_TEMPLATE.md`には、固定シナリオで参照文書、適用フロー、レビュー、検証を記録し、対象コミット時点の規則に照らして評価する手順がある。

既存の仕組みとの重複と目的の違いを確認し、ユーザー判断により追加実装を行わず終了する。

## 背景
コンテキスト選択、任意のワークフロー選択、変更影響に応じたレビュー選択を行うと、不要な参照を減らせる一方、ルーティング規則の変更によって必要な文書やレビュアーを誤って除外する可能性がある。
現状は代表例を人間が文書上で確認する方法が中心で、選択結果の回帰を継続的に検知する成果物がない。

## 課題
選択規則の変更が静かに品質ゲートを迂回すると、認証・認可、DB、API契約、ユーザー向け振る舞いなどの高リスク変更で必要なレビューや規則が適用されない。
毎回Agentの長い実行ログを人手で比較する方法は継続しにくい。

## 完了条件
- 代表的な依頼に対して、必要なコンテキスト、ワークフロー、レビュアー、検証の選択結果が再現可能である。
- 必須項目の欠落と不要な項目の追加が、選択規則の変更時に検出可能である。
- 既存の実装フローとレビュースキルの出力契約が維持されている。

## 実装方法案
- 代表依頼と変更対象を入力し、期待する対象領域、コンテキスト、ワークフローの適用有無、レビュアー、検証を宣言できる回帰ケース形式を定義する。
- 少なくとも、Controller名変更、テストだけの変更、予約テーブル列追加、認可規則変更、フロントエンド文言修正、BFF認証変更、APIと画面の横断変更をケース化する。
- 各ケースで`expected`だけでなく、読み込むべきでない文書や起動すべきでないレビュアーを`not expected`として検証できるようにする。
- 判定ロジックを機械実行可能な形にできる場合は自動テストを追加する。
  文書とAgent判断に残る部分は、固定入力に対する構造化結果の評価手順を用意する。
- 必須コンテキストやレビューの欠落を、不要な追加より高い重大度で失敗させる。
- 選択規則、索引、フローを変更する際に回帰ケースを実行する入口と、失敗時にどの条件が変わったか分かる出力を用意する。
- トークン量の測定はこのTODOへ混在させず、選択の正しさと再現性を対象にする。
