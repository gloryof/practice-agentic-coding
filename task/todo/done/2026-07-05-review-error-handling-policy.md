# 例外ハンドリング方針の見直し

## ステータス
- Status: Done
- Updated: 2026-07-12 - Domain の業務失敗を `DomainError` へ統一し、`ApiException` を関心事別分類へ集約して API エラーコードによる失敗種別の表現を明文化

## 背景
現在のエラーハンドリングでは、ドメインモデルやドメインサービスが返す業務エラーの表現と、API 境界で返す例外クラスの追加方針が十分に整理されていない。

予約申込の実装では `ReservationUnavailableReason` のように予約固有の理由コードを追加しているが、ドメインモデルで発生するエラー全体を統一的に扱うクラスや方針が明確ではない。そのため、今後の機能追加でコンテキストごとに個別の理由型やエラー型が増え、Usecase や Web レイヤでの変換ルールがばらつく懸念がある。

また、`ApiException` はエラータイプごとに個別の Exception クラスを追加する形になっている。どのような条件で新しい Exception クラスを追加し、どのような場合は既存の共通 Exception や details で表現するのかの判断基準が必要になっている。

## 影響
エラー表現の方針が曖昧なままだと、以下の問題が起きやすい。

- ドメイン層の業務エラーがコンテキストごとに異なる形で増え、Usecase で統一的に扱いにくくなる。
- Web レイヤの `UsecaseError` から `ApiException` への変換が肥大化し、同じ HTTP ステータスや同じエラー構造なのに Exception クラスだけが増える。
- API エラーコード、HTTP ステータス、details の使い分けが実装者ごとに揺れる。
- 新しい業務エラーを追加するときに、Domain / Usecase / Web のどこへ型を追加すべきか判断しにくい。

## 対応案
例外ハンドリング方針を見直し、少なくとも以下を整理する。

- ドメイン層の業務エラーを統一的に扱う型を導入するか、コンテキスト固有の理由型を許容する条件を定義する。
- `ReservationUnavailableReason` のような理由コード型を、ドメインモデル、ドメインサービス、Usecase エラーのどこまで露出させるかを決める。
- `UsecaseError` の役割を、業務エラーの集約型として維持するのか、コンテキスト別に分割するのかを検討する。
- `ApiException` の新規クラス追加条件を定義する。
  - HTTP ステータス、API エラーコード、レスポンス構造が既存と異なる場合のみ追加する。
  - 同じ HTTP ステータスとレスポンス構造で details の内容だけが異なる場合は、既存 Exception または共通 Exception で表現する。
  - クライアントが分岐に使う安定したエラーコードが必要な場合は、Exception クラス追加ではなくエラーコード追加で表現できないか先に検討する。
- 上記の判断基準を `api/docs/architecture.md` または `api/docs/coding-rule.md` に反映する。

## 確認方法
以下を確認する。

- 例外ハンドリング方針が API 開発ルールに明文化されていること。
- 既存の `UsecaseError`、`ApiException`、`UsecaseErrorMapper`、`ReservationUnavailableReason` の役割が説明できること。
- 新しい業務エラーを追加する場合に、Domain / Usecase / Web のどこへ型やコードを追加すべきか判断できること。
- Kotlin 変更を伴う場合は `api` ディレクトリで `./gradlew ktlintFormat` と `./gradlew check` が成功すること。

## 期限 / 優先度
優先度: 中。予約以外のコマンド機能で業務エラーや API エラーを追加する前に対応する。
