## 終了判断
検証の必須条件は、共通規則、領域別規則、各実装フローで定義されている。  
実装フローは変更の影響から検証を選び、実行結果を次工程へ渡し、修正後に影響する検証を再実行する。  
同じ全体検証の重複実行が現行フローで続いている具体例は確認されていない。  
ユーザー判断により、専用の`Verification Plan`契約や検証ランナーは追加せず、本TODOを終了する。

当初の完了条件に含めた「文書だけの変更では無関係な全体検証を選ばない」は達成していない。  
APIでは文書だけの変更も`api/AGENTS.md`と`api/docs/backend-guidelines.md`に従い、`./gradlew check`を実行する。  
この必須条件は今回変更せず、本TODOの`Done`は当初案の全面実装を意味しない。

## 確認した現行ルール
- APIは`./gradlew check`を必須とし、アダプター実装フローでは主要HTTPフローへの影響に応じてE2Eを選ぶ。
- フロントエンドは`frontend/docs/quality-and-nonfunctional-requirements.md`で`npm run check`、実APIブラウザE2E、複数ブラウザなどの条件を定める。
- フロントエンド実装フローは検証結果と省略理由をレビューへ引き継ぎ、修正後に影響する検証を再実行する。
- 文書変更はルート`AGENTS.md`に従い、`python3 scripts/check-docs.py`で変更対象のMarkdownを検査する。

## 当初案の扱い
- 領域横断の検証選択表、実行主体と結果の有効範囲を定める専用契約は追加しない。
- APIの文書変更に対する全体チェックの軽量化は行わない。
- 検証の重複や不足が具体的な作業で確認された場合は、その変更条件と現行ルールとの差分を調べて対応する。
