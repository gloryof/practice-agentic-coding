# 修正後動作確認の自動化（E2E含む）

## ステータス
- Status: Done
- Updated: 2026-05-17 - 起票
- Updated: 2026-05-24 - 完了（E2Eテストコード追加とJUnit通常テストからの分離実行を実装）
## 背景
- 現状、修正後の動作確認で `api/scripts/api/*/exec.sh` を個別に実行しており、毎回の確認手順が煩雑になっている。
- 認証トークン取得や前提確認を手でつなぐ必要があり、確認の抜け漏れが発生しやすい。
- E2E観点の最小回帰確認が定常化されておらず、修正影響の把握に時間がかかる。

## 影響
- 動作確認の実施コストが高く、修正サイクルが遅くなる。
- 手順が属人化し、実行順や確認観点の揺れによる品質リスクが増える。
- E2E観点の確認漏れにより、統合時の不具合を早期に検知しにくい。

## 対応案
- 修正後確認を1コマンドで実行できるランナーを整備する（例: 認証取得 -> 主要APIシナリオ実行 -> E2Eスモーク確認）。
- 実行前提（API起動、必要ツール、初期データ）と失敗時の終了条件を明確化する。
- 既存 `api/scripts` を再利用しつつ、実行順と結果判定を統一する。

## 確認方法
- 1コマンド実行で主要シナリオが完走し、成功/失敗が終了コードで判定できることを確認する。
- 異常系シナリオで意図どおりに失敗終了し、失敗箇所が特定できるログが出力されることを確認する。
- 最低1本以上のE2Eスモークシナリオが実行対象に含まれることを確認する。
