# サーバー・フロント実装フローを整備してスキル化を評価する

## ステータス
- Status: Done
- Updated: 2026-08-09 - 技術判断だけの依頼でpo-specを発動しない境界を明確化
- Updated: 2026-08-09 - 共通入口からサーバー・フロントエンド実装フローへ分離し、スキル化判定を完了
- Updated: 2026-08-02 - プロダクトデザイナーのフロントエンドフロー統合検討を追加
- Updated: 2026-07-20 - 起票

## 背景
現行の実装タスクフローはAPI、DB、HTTP E2Eなどサーバーサイドを中心に構成されており、フロントエンド固有の設計規則と検証手順を扱えない。

## 影響
単一フローのままフロント実装を開始すると、不要なサーバー向け手順の適用や、ブラウザE2E、アクセシビリティ、視覚確認の漏れが発生する。フローとスキルの責務を決めずに両方を作ると指示が重複する。

## 対応案
- `agents/flows/implementation-task-flow.md`を共通入口として維持し、対象領域の分類、active TODO確認、仕様影響判定、横断変更の順序、完了報告を集約した。
- API、DB、HTTP E2E、サーバー向けレビュー条件を`agents/flows/server-side-implementation-flow.md`へ分離した。
- BFFとClientの境界、画面設計、型検査、ビルド、ブラウザE2E、アクセシビリティ、視覚確認を`agents/flows/frontend-implementation-flow.md`へ定義した。
- 画面設計依頼では`product-designer`を主担当とし、画面、利用者フロー、主要操作、UI状態、レスポンシブ構成、デザインシステムの意味のある変更を含む実装ではレビューを必須とした。
- 横断変更は画面要件とAPI契約を整合した後、Spring Boot API、生成型・BFF・画面、実APIブラウザE2Eの順で進めることを決定した。
- サーバー、フロントエンドとも、広い実装トリガーとフローの重複を避けるためスキル化判定を`Keep as flow`とした。サーバーの反復手順は既存の`run-api-e2e`が所有し、フロントエンドの実行基盤は後続TODO 07・08が所有するため、新規スキル作成TODOは起票しない。
- ユーザー価値、業務上の振る舞い、データの意味または有効状態、受け入れ条件を新たに判断しない技術仕様・実装設計では、`po-spec`を発動しない境界をフローとスキルへ追加した。

## 確認方法
- サーバーのみ、フロントのみ、両方にまたがる代表依頼が、必要な仕様、ガイド、レビュー、検証へ到達できることを確認する。
- フロー間の責務重複、参照切れ、循環参照がないことを確認する。
- サーバーとフロントそれぞれのスキル化判定に、結論、根拠、スキルの責務、必要リソースが記録されていることを確認する。
- 画面設計依頼と画面を含む実装依頼が、プロダクトデザイナースキルの適用またはレビュー条件へ一意に到達できることを確認する。
- 技術規則だけで判断できる依頼が実装フローへ到達し、`po-spec`を発動しないことを確認する。
- スキル化を採用した場合、`task/todo/TEMPLATE.md` に準拠した後続TODOが起票されていることを確認する。
