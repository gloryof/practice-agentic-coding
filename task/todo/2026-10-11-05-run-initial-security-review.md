## 背景

自動検査だけでは業務上の認可や解析対象外のコードを確認しきれない。

## 課題

初回結果の評価と、修正後の再確認が未実施である。

子タスク02の実装検証では、以下の未評価の指摘を確認した。

| 対象 | 確認結果 |
|---|---|
| npm依存 | static入口の再検証でHigh 12件・Moderate 11件を検出 |
| Java依存 | 1,079 JARを全件識別し、3種類のCVEを構成間の重複込みで12件検出 |
| PostgreSQL | `postgres:16`で507件の指摘を検出し、High・Criticalを含む |
| Redis | `redis:7-alpine`でMediumの指摘を1件検出 |
| 秘密情報 | 当時のGit管理対象571ファイルで指摘なし |
| ソース | オンライン取得した196ルールファイルで265ソースを検査し、監査候補1件・解析エラーなし |

Javaの検出対象は`httpclient5:5.5.1`の`CVE-2026-64607`、`httpcore5:5.3.6`の`CVE-2026-54399`、`httpcore5-h2:5.3.6`の`CVE-2026-54428`である。  
それぞれの修正版は`5.6.3`、`5.4.3`以降と報告された。  
Redisの検出対象は`zlib:1.3.2-r1`の`CVE-2026-4738`で、修正版は`1.4-r0`と報告された。  
検査時のイメージdigestはPostgreSQLが`sha256:63e83b5a3dc36a917dccb76fe1bd2ac51f1ec9c1deb47ff20d4f04233bf6eae9`、Redisが`sha256:7f7d30b7fdd09467bac58198a1f166dd69789d348d4fe859cccb20e0cf287fbe`である。

これらは自動検査の検出結果であり、アプリへの到達可能性、誤検知、業務影響、更新互換性は未評価である。  
High・Criticalの指摘を受容済みとは扱わず、リリース判断の前に評価・修正・再検査を行う。  
Gradle本体、JDK、ビルドプラグインの公式情報による補完確認も未実施である。

npmの指摘は`@lhci/cli`、`lighthouse`、`puppeteer-core`などの開発依存経路を含む。  
npmが提示するダウングレード候補をそのまま採用せず、実際の依存経路と修正済みの互換版を確認する。

子タスク04の隔離ビルドでは、Next.js 16.4.3が既知脆弱性に関する更新推奨を表示して初回停止した。  
同じ検査用コピーで一度再実行するとビルドは成功したが、安全性の確認や修正完了を意味しない。  
リポジトリ管理者はnpm依存の評価と併せ、公式アドバイザリ、影響条件、互換性のある修正版を確認する。  
修正までは合成データだけのローカル検証に限定し、更新後にnpm依存検査、BFFの品質ゲート、ZAPを再実行する。

Semgrepの結果は、取得ルールの対象構文と単一関数解析の範囲内の結果である。  
KotlinのSQL文字列補間、Komapperのパラメーター束縛、独自TLS検証、公開ルールが列挙していないNode.jsのインポート形式、別関数で行う接続先検証、関数間・ファイル間の認証・認可は補完レビューが必要である。  
対象の詳細と再確認方法は[ルールの説明](../../scripts/internal/security/semgrep/README.md)を参照する。

オンライン取得へ変更した後、`frontend/eslint.config.mjs:27`で`detect-redos`の監査候補を検出した。  
ESLint設定の正規表現に対する指摘であり、実際の入力、正規表現の実行条件、性能への影響は未評価である。  
この候補もリポジトリ管理者が指摘の評価期限までに確認し、ソース検査で再確認する。

### ZAPの指摘候補と残る確認

子タスク04の最終設定では、次の4区分を検査してZAPの終了コード`1`を確認した。  
件数には同じルールの複数箇所と再試行時の候補を含み、独立した脆弱性の件数とは扱わない。

| 区分 | 指摘候補の内訳 | 合計 |
|---|---|---:|
| BFF・未認証 | Low 23、Medium 4、Informational 135 | 162 |
| API・未認証 | Informational 96 | 96 |
| BFF・認証済み | Low 24、Medium 14、Informational 136 | 174 |
| API・認証済み | Low 2、Informational 84 | 86 |

対応判定の対象となったルールIDは`10021`、`10023`、`10037`、`10038`、`10202`、`90022`である。  
対象ルートは実行時に表示し、変形されたパスは入力値の露出を避けて伏せる。  
リポジトリ管理者は各候補の影響と誤検知を評価し、修正後にZAPで再確認する。

途中の設定では、署名済みActionメタデータへの変形を含むBFF検査で`40018`のHigh候補と`30001`のMedium候補も出た。  
最終設定は署名済みメタデータを変形対象外とし、利用者の入力項目を検査する。  
候補が実際の脆弱性に当たるかは未評価であり、検査設定の調整だけを根拠に影響なしとは判断しない。

アプリ固有シナリオの接続・補完と手動レビューは未実施である。  
ZAP単体の完走を、初回の全体確認や指摘対応の完了とは扱わない。

## 完了条件

- static・dynamicの初回結果と未確認範囲が把握されている。
- コード・設定と認証・認可の補完レビューが行われている。
- 検出事項の影響、悪用条件、到達可能性が評価されている。
- 小規模な修正が行われ、対応する検査で再確認されている。
- 未解決事項を担当・期限・再確認方法付きのTODOで追跡できる。
- 管理者が手順に沿って検査を繰り返せる。

## 実装方法案

以下の順序で全体を確認する。

- 親タスクの一覧から子タスク01〜04の成果を確認する。
- staticとdynamicを実行し、結果を端末で確認する。
- 既存仕様に基づき、コード・設定と漏洩シナリオをレビューする。
- 既存のAPIテストとPlaywright E2Eで不足する確認を補う。
- 仕様や設計を変えない小さな修正を行い、再検査する。
- 大きな変更と残課題は重複を確認してTODOへ記載する。
- 手順と実測した制限を設計・実行説明へ反映する。
- 結果ファイルの保存やCI構築は追加しない。
- Java依存の指摘は用途別の依存経路と実行可能性を調べ、プラグイン側の管理版も踏まえて修正し、Java依存検査とAPI品質ゲートで再確認する。
- コンテナの指摘は検査時のdigestと現在のレジストリを照合し、公式イメージの更新・別タグの利用可否を評価して再検査する。
- 秘密情報検査は後続の追加ファイルもGit管理対象に含めて再実行する。
- npm依存の指摘は開発ツールの実行条件を含めて影響を評価し、互換性を確認して更新後にnpm依存検査を再実行する。
- Semgrepの対象外を補完レビューし、対象構文の追加が必要な場合は固定ルールとfixtureを更新してソース検査を再実行する。
- シナリオをdynamicへ接続する際は、準備・ビルドを除くZAPとシナリオの合計を30分以内に管理する。
