# 実装コンテキストの軽量ルーティングを追加する

## ステータス
- Status: Proposed
- Updated: 2026-08-16 - 起票

## 背景
現行の実装フローは、対象領域と仕様影響を分類し、`api/docs/backend-guidelines.md`では詳細文書の参照条件も定義している。一方、フロー、`AGENTS.md`、領域別ガイドに分散した選択結果を一つの軽量なルーティング情報として再利用する契約はなく、必要文書を決めるまでに前提文書や参照先を連鎖的に読む可能性がある。

すべての詳細文書を読んでから必要性を判定する方式では、選択処理自体がコンテキスト削減効果を失う。

## 影響
変更に無関係なテスト、DB、セキュリティ、ドメイン、画面設計などの詳細規則まで読み込むと、実装前のコンテキストが増え、重要な規則と対象コードへ使える余地が減る。反対に参照条件を緩めすぎると、必須規則の見落としにつながる。

## 対応案
- ユーザー要求、変更候補領域、既存の対象領域分類、仕様影響ゲートから参照先を選ぶ、短いコンテキスト選択契約を定義する。
- サーバー、フロントエンド、横断、リポジトリ共通の各分類について、常時参照する`required`と変更条件で追加する`conditional`を明示する。
- テスト、DB、認証・認可、API契約、UI、運用・非機能、ドメイン仕様などの条件から詳細文書へ到達する軽量な索引を整備し、詳細規則そのものは重複記載しない。
- 選択結果として、対象領域、仕様影響、選択した文書、選択理由、除外した主要文書と理由を後続工程へ渡せる最小形式を定義する。
- 変更対象が調査中に広がった場合だけ再選択し、初期選択を固定して必要な規則を見落とさないようにする。
- 専用`implementation-context`スキルは先に前提とせず、反復可能な選択手順や補助リソースをフローから分離する必要が実測で確認された場合だけ採用する。採用する場合も、スキル自身が詳細文書を全件読まない構成にする。
- `task/todo/done/2026-07-18-05-make-spec-context-references-conditional.md`で導入済みの仕様影響ゲートを正本として再利用し、同じ判定を追加しない。

## 確認方法
- 軽微なコード修正、テスト変更、DB変更、認証・認可変更、API契約変更、画面変更の例で、必要な文書だけが一意に選ばれる。
- 変更条件に一致しない詳細文書を、選択判定のために先読みしない。
- 変更範囲の拡大時に選択結果を更新し、必要な規則を追加できる。
- 同じ規則の本文が索引、フロー、開発ガイドへ重複していない。
- `task/todo/2026-08-16-02-measure-agent-workflow-context-baseline.md`の基準値より、必要コンテキストの割合が悪化しない。
- 文書変更後に`./scripts/check-no-local-paths.sh`が成功する。
