# ワークフローごとの検証選択を定義する

## ステータス
- Status: Proposed
- Updated: 2026-08-16 - 起票

## 背景

`task/todo/2026-08-16-05-classify-task-size-and-select-workflow.md`では、対象領域、変更の焦点、タスク規模に応じて、適用するワークフローとレビューを選択する予定である。
一方、選択後の各ワークフローが、変更範囲とリスクから必要な検証、実行主体、再実行条件を返す共通契約は定義されていない。

現状は領域ごとに検証条件の粒度が異なる。

- APIでは`api/AGENTS.md`と`api/docs/backend-guidelines.md`が、実装またはレビュー結果の共有前に、変更種別を区別せず`./gradlew check`を必須としている。
- フロントエンドでは`agents/flows/frontend-implementation-flow.md`に変更条件別の検証表があるが、`frontend/`の実装変更すべてに対する`npm ci`と`npm run check`、E2E、性能、複数ブラウザ、手動確認の選択と再実行範囲を、タスク規模分類やレビュー担当の責務と接続していない。
- リポジトリ共通変更、プロダクト仕様・ユーザーストーリー、技術方針文書では、対象文書固有の検査とルートの文書検査をどこで選択するかがワークフローごとに揃っていない。
- Main Agentと複数のレビュー担当が、同じ全体検証を個別に再実行するか、既存結果を共有するかの所有境界がない。

`agents/benchmarks/baselines/20260830-dd4b1f6-fullrun-official/07-api-architecture-policy.md`では、APIアーキテクチャ方針文書とTODOだけの変更に対して、Main Agentと複数のレビュー担当が`./gradlew check`を実行した。
変更と無関係なPostgreSQLテスト17件がDocker client不在で失敗し、失敗原因の調査と再実行が発生した。
これはGradle固有の問題ではなく、ワークフロー選択と検証選択、検証結果の引き渡しが分離していることによる一例である。

## 影響

低リスクまたは文書だけの変更へ広いビルド、テスト、E2E、性能検査、手動確認を適用すると、完了時間、計算資源、Agentのコンテキストとトークン使用量が増える。
環境依存の検証を変更条件と無関係に実行すると、成果物起因ではない失敗の調査やTODO起票が増え、本来の変更リスクが埋もれる。

一方、検証を個別判断だけで省略すると、Kotlin、TypeScript、DB、認証、HTTP契約、画面、アクセシビリティ、ブラウザ互換性などへの影響に必要な品質ゲートが欠落する可能性がある。
タスク規模だけで検証を決めると、小さな認可変更やmigration変更のように、差分は小さくても高リスクな変更を軽く扱う危険もある。

## 対応案

- 優先度5のTODOで確定する対象領域、変更の焦点、タスク規模、選択ワークフローを入力として、各ワークフローが`Verification Plan`を返す契約を定義する。
- `Verification Plan`には少なくとも次を含める。
  - 選択した自動検証、E2E、静的検査、文書検査、手動確認。
  - 各検証を選択した変更条件とリスク。
  - 主要な非適用検証と省略理由。
  - 実行主体、実行順序、環境前提、結果の有効範囲。
  - レビュー指摘または変更範囲拡大後の再実行条件。
- タスク規模は検証量を調整する一要素とし、セキュリティ、DB、契約、移行、利用者影響などのリスク条件を優先する。
- 各ワークフローで、変更条件から検証を選ぶ正本を一つだけ定義する。
  - サーバー実装: Kotlin、Gradle・依存関係、DB・migration、Repository・トランザクション、HTTP契約、認証・認可、技術方針文書、テストだけの変更を区別する。
  - フロントエンド実装: TypeScript・BFF・Client、UI・CSS、認証、API型、依存関係、Storybook、ブラウザ互換性、性能、文書だけの変更を区別し、既存の変更条件表を再評価する。
  - 横断実装: サーバーとフロントエンドの計画を和集合にし、契約整合と実APIブラウザE2Eなど境界固有の検証だけを追加する。
  - リポジトリ共通実装: CI、スクリプト、ルール、ワークフロー文書、Markdownなど、変更した仕組みのfixtureまたは自己検証を選択する。
  - プロダクト仕様・ユーザーストーリー: 正本・索引・リンク・文書規則・受け入れ条件の整合確認を選択し、実行時成果物へ影響しない場合はビルドを要求しない。
- 文書だけの変更では、ローカル絶対パス検査、変更ファイル限定Lint、リンク・索引・構造検査など、文書の種類に対応する検証を選択する。
  - 実行時成果物、生成物、アーキテクチャテストと結合していない場合は、Gradleやnpmの全体ゲートを理由なく実行しない。
  - 文書がコード生成、ビルド入力、機械検査fixture、実行時設定を兼ねる場合は、文書拡張子だけを理由に軽量化しない。
- Main Agentを共通品質ゲートの最終所有者とする。
  - `task/todo/2026-08-16-04-pass-review-context-packages.md`の`Review Context Package`へ、`Verification Plan`と実行済み結果を含める。
  - レビュー担当は共有結果の対象コミット、差分、実行条件が現在のレビュー対象と一致することを確認し、専門判断に必要な追加検証だけを実行する。
  - 各レビュー担当が同一の全体ビルド、全テスト、E2Eを理由なく再実行しない。
  - 独立性が必要なセキュリティ検査、DB検査、QA再現、レビュー指摘の証明は、追加実行理由を記録して実施する。
- 指摘反映後は、変更されたファイルとリスク条件から`Verification Plan`を更新する。
  - 影響した対象検証だけを再実行する。
  - 変更範囲が上位分類へ広がった場合は検証を追加する。
  - 全体ゲートが完了条件となる変更では、最終差分に対してMain Agentが一度統合実行する。
- `AGENTS.md`には常時適用する検証原則と各ワークフローへの入口だけを置き、具体的な選択表を重複記載しない。
- 実測で同じ検証セットの起動、環境準備、結果収集が反復される場合だけ、検証ランナーのスキルまたは共通スクリプト化を検討する。

## 確認方法

- 優先度5のTODOで定義する`trivial`、`normal`、`complex`の代表例から、対象ワークフローと`Verification Plan`が一意に選ばれる。
- 小規模な認可変更、migration変更、依存関係変更で、規模が小さいことを理由に必須のセキュリティ、DB、供給網検査が省略されない。
- API技術方針文書だけを変更したケースで、実行時成果物との結合がなければ`./gradlew check`とHTTP E2Eが選択されず、文書検査と差分検査が選択される。
- Kotlin、トランザクション、HTTP契約を変更した各ケースで、対象テスト、全体ゲート、DB統合、HTTP E2Eの必要な組み合わせが選択される。
- フロントエンドの文言だけ、BFF認証、API型、UI・CSS、依存関係を変更した各ケースで、`npm run check`、Storybook、ブラウザE2E、性能、複数ブラウザ、auditの必要・不要が区別される。
- APIと画面の横断変更で、領域別検証に加えて契約整合と実APIブラウザE2Eが一度だけ選択される。
- ユーザーストーリー、技術方針、ルール文書、CIスクリプトの各変更で、成果物種別に対応する文書検査、fixture、自己検証が選択され、無関係なアプリケーションビルドが選択されない。
- 複数の専門レビュー担当を起動したケースで、共通検証結果が`Review Context Package`から共有され、理由のない全体検証の重複実行がない。
- レビュー指摘で実装コードへ変更が広がった場合は必要なビルドとテストが追加され、文書だけの指摘反映では文書検査だけが再実行される。
- 検証を省略した完了報告から、ワークフロー、変更条件、リスク、判断根拠、代替検査を追跡できる。
- 必須検証を意図的に除外した回帰ケースと、不要な全体検証を意図的に追加した回帰ケースの両方が失敗する。
- 改善前と同じベンチマークシナリオを再実行し、成果物品質を維持したまま、検証の重複回数、環境起因失敗の調査時間、処理時間、実トークンまたは代替指標が悪化しない。
- 文書変更後に`./scripts/check-no-local-paths.sh`が成功する。
