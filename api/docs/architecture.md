# アーキテクチャ
## 基本方針
オニオンアーキテクチャとCQRSを組み合わせたアーキテクチャを採用する。
コマンドとクエリごとで例やルールを設ける

### 採用理由
- ドメインモデルを中心としてメンテナンスしやすくするため
- WriteモデルとReadモデルを一緒にしているとモデルが肥大化するため

## 適用ルール
対象となる機能がどちらに含まれるかは以下のルールに従うこと

### コマンド
- 業務上、何かしらの情報について記録や更新を含む

### クエリ
- 情報を参照するのみで業務上の情報について記録や更新を含まない

### 例外規定
- ログの記録についてはコマンド/クエリの判定条件位は使わない

## コマンド/クエリ共通
### 例外ハンドリング
- 業務失敗は `kotlin-result` で表現し、失敗を合流可能な形で連鎖する。
- プロダクトコードで業務制御のために例外を送出するのは Web レイヤのみに限定する。
- `RuntimeException` は握りつぶさず伝播させ、共通ハンドラで `500` に変換する。
- Domain/Usecase が業務エラーを例外で表現しない。
- 想定外の技術障害（DB障害、ライブラリ障害など）は業務エラーへ偽装せず、例外伝播させる。
- レイヤごとのエラー型は単一の共通型（例: `DomainError`, `UsecaseError`）へ集約する。
- Usecase の公開メソッドは `Result<Success, UsecaseError>` を返し、失敗を合流可能な形で連鎖する。
- Web レイヤで `UsecaseError` を `ApiException` に一元変換するマッパーを利用する。

### DBアクセス
- Infra レイヤのDBアクセスは Komapper を使用する。
- 例外が必要な場合は 8.1 の規約例外に従う。

### Repository

#### 命名
- Repositoryの実装クラス名は `{InterfaceName}Impl` で終える。
- 実装が複数ある場合は `{InterfaceName}{Qualifier}Impl` とする（例: `AuthAccountRepositoryReadReplicaImpl`）。

#### 実装単位
- 1つの実装クラスで複数のRepositoryインターフェースを実装しない。
- 1インターフェースにつき1実装クラスを基本とし、責務境界を明確に保つ。

### Web
- JSONプロパティは `snake_case` を使用する。
- 意味を持たない `null` フィールドは返却しない。
- 日時はISO8601形式で返却する。

#### バージョニング
- APIバージョンはURLで管理する（例: `/api/v1/...`）。
- 破壊的変更時は新バージョンを追加し、既存バージョンを即時削除しない。
- 廃止予定バージョンには期限を明示する。

#### エラーとバリデーション
- 入力検証は Web 境界で実施し、失敗時は `400 Bad Request` を返す。
- エラーレスポンスは共通形式とし、`code`、`message`、`details`、`trace_id` を含める。
- スタックトレースや内部実装情報をクライアントへ返却しない。

### 日付
- 日時の保存および演算はUTC前提で行う。

### 観測性・ログ
- すべてのリクエスト処理で `traceId` を追跡可能にする。
- ログへ機微情報（認証情報、個人情報）を平文出力しない。
- 障害解析に必要な最低限の構造化情報（イベント名、結果、主要ID）を出力する。

## コマンド
### レイヤー
以下のレイヤーによる分割を行う。
- Domain
- Usecase
- Web
- Infra

### パッケージ構成
コマンド側の標準構成は以下とする。
 
- `jp.glory.practice.agentic.{コンテキスト境界}.command.domain`
- `jp.glory.practice.agentic.{コンテキスト境界}.command.usecase`
- `jp.glory.practice.agentic.{コンテキスト境界}.command.web`
- `jp.glory.practice.agentic.{コンテキスト境界}.command.infra`

### 依存
コンテキスト境界を跨いだ依存はさせない。
`shared` に関しては各レイヤから参照して良い。

また、各レイヤごとに依存して良いレイヤのルールを設ける。
ただし、以下のライブラリはレイヤを横断して使用して良い。

- kotlin-result

### Domain
#### 責務
業務ロジックと不変条件を担い、技術的要因に依存しない。

#### 依存して良いレイヤ
- Domain

#### ドメイン分類
- `model`: ドメインモデル。用語はユビキタス言語と同期する。
- `event`: 業務イベント。可能であればモデルから生成する。
- `service`: 業務処理。技術要因を含まない処理はクラス、技術要因を含む処理はインターフェースを定義する。
- `repository`: ドメインモデル復元のためのインターフェースのみを定義する。

#### 設計方針
- `event` のプロパティは、可能な限り `model` で定義された型（値オブジェクトやモデル）を参照し、プリミティブ型の重複定義を避ける。
- `repository` の公開メソッド（引数・戻り値）は、原則としてドメインモデル/値オブジェクトを使用し、`String` などのプリミティブ型を露出しない。
- 技術的制約でプリミティブ型が不可避な場合のみ例外を認める。この場合はPRに必要性、影響範囲、解消計画を記載する。

### Usecase
#### 責務
Domain モデルを使って利用者の操作要求を実現する。

#### 依存して良いレイヤ
- Domain
- Usecase

### 設計方針
- ユースケースの入力を表す `Input`、戻り値を表す `Result` クラスを定義できる。

### Web
#### 責務
HTTP 入出力の変換と Usecase 呼び出しのみを行う。

#### 依存して良いレイヤ
- Usecase
- Web

#### HTTPメソッド
- コマンドAPIは `POST`、`PUT`、`PATCH`、`DELETE` のみを使用する。
- コマンドAPIに `GET` を使用しない。
- 1つのAPIは1つの状態変更責務に限定する。

#### リクエスト/レスポンス
- API入出力はDTOで定義し、Domainモデルを直接公開しない。
- JSONプロパティは `snake_case` を使用する。

### Infra
#### 責務
DBや外部サービス、ライブラリ連携など技術的処理を担当する

#### 依存して良いレイヤ
- Infra
- Repositoryはインターフェイスの実装のみは許可

## クエリ

### レイヤー
以下のレイヤーによる分割を行う。
- Usecase
- Web
- Infra

### パッケージ構成
コマンド側の標準構成は以下とする。

- `jp.glory.practice.agentic.{コンテキスト境界}.query.web`
- `jp.glory.practice.agentic.{コンテキスト境界}.query.usecase`
- `jp.glory.practice.agentic.{コンテキスト境界}.query.infra`

### Usecase
#### 責務
参照要件の組み立てとレスポンス向け整形を担当する。

#### 依存して良いレイヤ
- Usecase

#### 設計方針
- RepositoryはUsecaseごとに作成する

### Web
#### 責務
HTTP 入出力の変換と Usecase 呼び出しのみを行う。

#### 依存して良いレイヤ
- Usecase
- Web

#### HTTPメソッド
- クエリAPIは `GET` のみを使用する。
- クエリAPIで状態変更を行わない。
- クエリAPIで `POST`、`PUT`、`PATCH`、`DELETE` を使用しない。

#### 検索条件・応答
- 検索条件、ページング、ソートはクエリパラメータで表現する。
- クエリレスポンスは読み取り最適化DTOで定義する。
- 取得失敗時のエラーは共通エラー形式で返却する。

### Infra
#### 責務
参照用データ取得（DB検索、外部参照）を担当する。

#### 依存して良いレイヤ
- Infra
- Repositoryはインターフェイスの実装のみは許可
