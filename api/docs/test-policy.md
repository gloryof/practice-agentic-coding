# テスト

## ユニットテスト

### 目的
ユニットテストは以下の目的で実施する。
- 動作する仕様としての活用
- リファクタリングをしやすくする
- リグレッションしていないことの確認

### 作成対象外
以下のクラスはユニットテスト作成の対象外とする

- フレームワークの設定クラス

### 設計指針
- 単体テストは1クラス単位の振る舞い検証を基本とする
- 単体テストでレイヤを跨ぐ依存を差し替える場合は MockK を利用する
- 入力に対して出力が正しいかを確認する
- 戻り値があるメソッドは、値が正しいことを検証する
- 戻り値がないメソッドは、副作用で設定される値が正しいことを `verify`/`capture` で検証する。
- オブジェクトの全ての値が正しいかを確認する
  - UUIDなどのランダム値は一致検証を不要とし、存在・形式のみ検証してよい
- テスト名は期待動作が読める形式にする
- 振る舞いに関係しない内部実装の詳細を過度にモックしない
- 単体テストで匿名継承による `object` テストダブルを新規追加しない
- 一覧/検索などコレクションを返す処理は、0件と複数件のケースをテストで検証する

### Domainレイヤ
- 単体テストで業務ルールと不変条件を検証する

###  Usecaseレイヤ
- 成功フローと失敗フロー、および副作用の有無を検証する
- Queryの場合は検索条件の解釈と結果整形を検証する。

### Infraレイヤ
- Repository実装はDB統合テストを用意し、永続化契約（保存・取得・存在判定）を検証する。
- DB統合テストは単体テストの実行範囲に含める

### Webレイヤ
- コマンドの場合は更新系HTTP契約（メソッド、ステータス、エラー形式）を検証する
- クエリの場合は`GET` 契約、ページング、ソート、フィルタを検証する。
