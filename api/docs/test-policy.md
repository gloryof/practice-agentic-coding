# テスト

## 規範語
- `MUST`: 必須。満たさない変更は受け入れない。
- `MUST NOT`: 禁止。いかなる理由でも実施しない。
- `SHOULD`: 強く推奨。満たさない場合は理由を説明する。
- `MAY`: 任意。文脈に応じて選択できる。

## ユニットテスト

### 目的
- `MUST` ユニットテストを動作する仕様として活用する。
- `MUST` ユニットテストをリファクタリング容易性の担保に使う。
- `MUST` ユニットテストでリグレッションしていないことを確認する。

### 作成対象外
- `MUST NOT` フレームワークの設定クラスに対してユニットテストを新規作成する。

### 設計指針
- `MUST` 単体テストは1クラス単位の振る舞い検証を基本とする。
- `MUST` `@Test` が2件以上あるテストクラスは、`@Nested` でメソッド単位または状態単位にグルーピングする。
- `MAY` `@Test` が1件のみのテストクラスは `@Nested` を省略してよい。
- `MUST` 単体テストでレイヤを跨ぐ依存を差し替える場合は MockK を利用する。
- `MUST` 入力に対して出力が正しいことを検証する。
- `MUST` 戻り値があるメソッドは返却値の正しさを検証する。
- `MUST` 戻り値がないメソッドは、副作用で設定される値を `verify` または `capture` で検証する。
- `MUST` オブジェクトの値が正しいことを検証する。
- `MAY` UUIDなどのランダム値は一致検証を省略し、存在・形式のみ検証してよい。
- `MUST` テスト名は期待動作が読める形式にする。
- `MUST` テスト名は `given ... when ... then ...` 形式で記述する。
- `SHOULD` 振る舞いに関係しない内部実装の詳細を過度にモックしない。
- `MUST NOT` 単体テストで匿名継承による `object` テストダブルを新規追加しない。
- `MUST` 一覧/検索などコレクションを返す処理は、0件と複数件のケースを検証する。

### Domainレイヤ
- `MUST` 単体テストで業務ルールと不変条件を検証する。

### Usecaseレイヤ
- `MUST` 成功フローと失敗フロー、および副作用の有無を検証する。
- `MUST` Query の場合は検索条件の解釈と結果整形を検証する。
- `MUST` Queryの結果DTOがステータス分岐を持つ場合、各分岐ケースで主要プロパティを検証する。
- `MUST` 技術障害時の振る舞い（例外送出またはフォールバック返却）を仕様として固定し、テストで明示的に検証する。

### Infraレイヤ
- `MUST` DAO実装はDB統合テストを用意し、永続化契約（保存・取得・存在判定・集計）を検証する。
- `MUST` Repository/QueryImplがDAOへ委譲する構成の場合、Repository/QueryImplはMockKによるユニットテストで入出力変換と委譲契約を検証する。
- `MUST` DB統合テストは単体テストの実行範囲に含める。

### Webレイヤ
- `MUST` コマンドの場合は更新系HTTP契約（メソッド、ステータス、エラー形式）を検証する。
- `MUST` クエリの場合は `GET` 契約、ページング、ソート、フィルタを検証する。
