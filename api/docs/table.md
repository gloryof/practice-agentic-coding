# テーブル

## 基本方針
* **DBは最終防衛ライン:** アプリケーション側の不備やAIの推論ミスによる不正データ混入を防ぐため、DB層で厳格な制約（型・制約）を課す。
* **ビジネスドメイン優先:** 業務要件に直結するデータ構造のみを定義し、スキーマのノイズを最小化する。
* **責務の分離:** 「現在の状態（State）」と「発生した事実（Event）」を明確に分け、ドメインモデルの整合性と監査耐性を両立させる。

## 設計方針

###  型と制約
* **状態管理:** 状態（Status）は PostgreSQL のネイティブ **Enum** を使用する。定義はアプリケーションコードを正とし、DB側を同期させる。
* **整合性の担保:** `NOT NULL`、`CHECK`、`FOREIGN KEY` 制約を徹底し、AIが制約を無視したコードを生成できない環境を作る。
* **NULL許容:** すべてのカラムは原則 `NOT NULL` とし、業務上 `NULL` が必要な場合のみ例外を認める。
* **UUID:** アプリケーション側で UUIDv4 を発行し、DB には `VARCHAR(36)` で保存する。
* **時刻カラム:** `TIMESTAMP WITHOUT TIME ZONE` を使用する。
* **文字列長:** 業務要件に基づく上限を設け、未確定の場合でも仮の上限を設定する（例: 255）。

### パフォーマンスと排他制御
* **インデックス:** 全ての外部キー（FK）には原則インデックスを付与する。
* **リスクベースの排他制御:** 原則は「後勝ち（Last Commit Wins）」とし、シンプルさを優先する。
* **致命的不整合の回避:** 貸出や予約など、不整合が致命的となる操作（早い者勝ち）に限り、`version` カラムによる **楽観的ロック** を実装する。
* **多対多:** 中間テーブルは複合主キーを持ち、片側検索を想定する列に追加インデックスを付与する。

### データの永続性と履歴
* **メタデータ:** `created_at` 等の監査カラムは、業務上必要とされる場合（貸出日、登録日等）を除き、原則として付与しない。
* **履歴の分離:** 状態の変化を追跡する必要があるドメインは、本体とは別に **Append-Only（挿入のみ）** の履歴テーブルを作成する。

## 識別子と命名ルール
* **テーブル名:** `snake_case` の複数形に統一する（例: `library_users`, `book_items`）。
* **カラム名:** `snake_case` に統一する。
* **PK/FK命名:** 主キーは `id`で統一し、外部キーは `参照先テーブル名_id`（参照先テーブルは `snake_case` 複数形）とする。
* **外部キー制約名:** `fk_{table}_{ref_table}` 形式に統一する。
* **インデックス名:** `idx_{table}_{column}` に統一する。

## 機械チェック（SQLFluff）
* **実行要件:** AIがDBテーブル設計やFlywayマイグレーションを変更した場合、作業完了後にSQLFluffチェックを実行する（`api` ディレクトリで実行）。
* **ルール指定:** SQLFluffのルール指定は番号ではなくエイリアス（`agentic.*`）で管理する。

```sh
python3 -m venv .venv
.venv/bin/pip install -r requirements/sqlfluff.txt
.venv/bin/sqlfluff lint --config .sqlfluff src/main/resources/db/migration
```
