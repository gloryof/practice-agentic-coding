# 情報漏洩対策の設計

## 目的
AI技術が発達したことにより脆弱性をついた攻撃も増えている。  
情報漏洩につながる弱点を悪用される前に発見し、対処できる仕組みを構築する。

## ゴール

- 情報漏洩につながる弱点を検出できる。
- 検出事項の影響と悪用条件を評価できる。
- 修正または残課題として追跡し、再検査できる。
- 同じ範囲の確認を手動で繰り返せる。
- 新しい攻撃や脆弱性に合わせて検査を更新できる。

## 検査対象

以下のアプリと構成要素を対象とする。

- Spring Boot API
- Next.js BFF
- ブラウザで動作するフロントエンド
- PostgreSQLとRedisのコンテナ
- 依存関係
- コードと設定
- 現在のGit管理対象ファイルに含まれる秘密情報

### 検査対象外

以下の内容は、各項目の理由により初期対象外とする。

- **Git履歴全体：** 現在のコードと構成の確認を優先するため。
- **未追跡の個人設定：** リポジトリから再現できる共通構成を対象とするため。
- **本番基盤の構築：** 現在はデプロイせず、ローカルの検査専用環境を使用するため。
- **CI構築と定期自動実行：** 今回の範囲は手動実行できる検査スクリプトの整備までとするため。
- **脆弱性・侵害情報の自動収集と継続監視：** 使用製品の公式情報を手動で確認する範囲とするため。
- **クラウドへのコード送信：** 検査はローカルで実行し、外部へのコード提供を不要とするため。
- **漏洩後の対外対応訓練：** 今回は漏洩につながる弱点の発見と対処に範囲を絞るため。
- **利用者向けAPIと業務仕様の変更：** 既存の仕様を基準に安全性を確認するため。
- **検査目的での未実装機能の追加：** 実装済み機能の安全性を確認するため。

## 検査の完了条件

各回の検査は、以下の状態で完了とする。

- 対象の検査が実施され、結果が確認されている。
- 未実施・失敗した範囲と理由が把握されている。
- 検出事項の影響が評価されている。
- 修正済みの事項が再検査されている。
- 未解決事項の担当、期限、再確認方法が記録されている。

## 運用フロー

確認から対応まで、以下の順序で実施する。

1. 実施のきっかけとなる情報を確認する。
2. 検査情報を更新し、専用環境を準備する。
3. 検査とコード・設定のレビューを実施する。
4. 結果を評価する。
5. 修正または残課題を記録する。
6. 対応した検査を再実行する。
7. 検査環境を片付ける。

### 実施のきっかけ

検査は管理者が手動実行し、以下を実施のきっかけとする。

- 管理者が確認時期を判断したとき
- 使用製品に関係する重大な脆弱性・侵害情報を把握したとき
- 依存関係、認証、公開設定の変更

関連する情報は以下の方法で確認する。

- 使用製品の公式アドバイザリを確認元とする。
- 重大な脆弱性・侵害情報を把握したら、公式情報の影響バージョンと対処方法を確認する。
- 使用バージョンへの影響を判断し、関連する検査を実行する。
- 検査DBへの反映を待たず、必要な対応を判断する。
- 対応事項はTODOへ記載する。

### 準備と検査

以下の条件で検査を実施する。

- 定期実行の自動設定は有効化しない。
- CI環境は構築しない。
- 将来のCI連携でも呼び出せるよう、検査処理はスクリプトにまとめる。
- 検査専用環境を先に整備し、実行後に結果を読み解く。
- 脆弱性DBは実行時に更新する。
- 新しい攻撃に関係する検査とシナリオを追加する。

ツール、ルール、アドオン、イメージは以下の方法で更新する。

- 検査内容を見直すときや、関連する脆弱性を把握したときに手動更新する。
- 供給元と変更内容を確認する。
- 対応バージョンの範囲内で最新安定版を選ぶ。
- 更新後のバージョンを固定する。
- コンテナイメージはdigestも固定し直す。
- 該当する検査グループを実行し、検査が動作することを確認する。
- 自動更新の仕組みは追加しない。

### 結果の評価と対応

結果は以下のように分けて扱う。

- 検出がない場合は、確認範囲と未確認範囲を確認する。
- 検出した場合は、影響、悪用条件、到達可能性、誤検知の根拠を評価する。
- 検査に失敗した場合は、原因を確認して再実行する。
- 認証失敗、情報更新失敗、タイムアウト、未実施を問題なしと扱わない。

評価後は以下の方針で対応する。

- 仕様や設計を変えない小規模な修正は今回実施する。
- 修正後は対応する検査を再実行する。
- 大きな変更と未解決事項は、[TODO運用ルール](../../task/todo/README.md)に従って追跡する。
- TODOは既存事案との重複を確認する。
- 未解決事項には担当、期限、緩和策、再確認方法を記録する。
- Critical・Highを維持する場合は、期限付きのリスク対応と補完統制を記録する。
- アプリ固有の不備は回帰テストやレビュー項目に追加する。
- 検査ツール自身の侵害や脆弱性は、使用停止、影響、更新、代替を評価する。

## 検査方法

実装済みの範囲とコマンドは[セキュリティ検査の実行方法](security-checks.md)を参照する。

以下の方法を組み合わせて確認する。

- 依存関係の既知脆弱性検査
- コンテナイメージの既知脆弱性検査
- ソースコードの静的検査
- 秘密情報検査
- 起動したアプリの動的検査
- アプリ固有の漏洩シナリオテスト
- コードと設定のレビュー

### 検査環境と共通の実行方法

#### Compose構成と実行場所

検査の実行基盤は以下の構成とする。

- リポジトリ直下の `compose.security.yml` に検査用サービスを定義する。
- 開発用のComposeファイルは変更しない。
- Composeプロジェクト名は `security-check` とする。
- 開発用の固定コンテナ名 `agentic-postgres` は使用しない。
- PostgreSQLとRedisをComposeで起動する。
- PostgreSQLとRedisは `127.0.0.1` にだけポートを公開する。
- DBの保存領域は検査専用にする。
- Trivy、Semgrep CE、ZAPは検査時だけ `docker compose run --rm` で実行する。
- npm auditは検査用Node.jsサービスで同様に実行する。
- Playwrightは既存のE2E実行方法を活用する。
- Playwright専用のComposeサービスは追加しない。
- APIとBFFは既存の起動方法を再利用し、ローカルで起動する。

#### 開発環境との分離

開発環境との競合を以下の方法で防ぐ。

- API、BFF、PostgreSQL、Redisは開発用と同じポートを使用する。
- 開発環境と検査環境は同時に起動しない。
- 動的検査で使用するポートが一つでも使用中なら、環境の作成やDBの初期化前に終了する。
- APIとBFFには検査用DB・Redisへの接続設定を使用する。
- 合成データを使用する。
- 検査用のプロセス、Composeプロジェクト、ネットワーク、DB、保存領域を開発環境と分ける。
- 動的検査の対象を検査専用環境に限定する。

#### 起動と片付け

検査用環境は以下の方法で管理する。

- API起動は[API起動・E2Eスキル](../../.codex/skills/run-api-e2e/SKILL.md)のランナーを環境指定に対応させる。
- 検査専用操作でmigration、seed、起動、終了を集約する。
- 開発用DBを削除して再作成する既存操作を、そのまま呼び出さない。
- ポート競合や起動失敗の後に、既存サービスへ接続して続行しない。
- 正常終了、異常終了、中断時とも、当該実行が作成した資源だけを片付ける。

起動ランナーは以下のインターフェースとする。

- `run.sh start --env security`で検査用環境を起動する。
- `run.sh stop --env security`で検査用環境を停止する。
- `--env dev`で開発用環境を指定する。
- `--env`の省略時は従来の開発用動作を維持する。
- 停止と片付けは、指定した環境が所有する資源だけを対象にする。

#### 検査コマンドとグループ

チェック処理は以下の構成とする。

- 各チェック処理を別スクリプトに分け、個別に実行できる構成とする。
- 共通の入口は `static` と `dynamic` の2グループを提供する。

検査コマンドは以下のインターフェースとする。

- `./scripts/run-security-checks.sh --group static`でアプリ起動不要の検査を実行する。
- `./scripts/run-security-checks.sh --group dynamic`でアプリ起動を伴う検査を実行する。
- 初期は `--only` と `--all` を用意しない。
- 個別の再実行は各チェック用スクリプトから行う。

グループは以下の範囲で分ける。

- `static`は依存関係、コンテナイメージ、ソースコード、秘密情報を検査する。
- `static`ではAPI・BFF・DB・Redisを起動しない。
- `static`ではGradleでJava依存関係を解決し、検査用ディレクトリへ抽出する。
- `dynamic`は専用環境を起動し、ZAPとアプリ固有の自動シナリオ検証を実行する。
- コードと設定の手動レビューはグループの実行とは別に行う。

#### ツールとイメージのバージョン

ツールとイメージの版は以下の方針で選ぶ。

- 導入時点の最新安定版を採用する。
- リポジトリで対応バージョンが指定されている場合は、その範囲内の最新安定版を選ぶ。
- 採用版と既存アプリの互換性を確認する。
- 具体的なバージョンを固定する。
- コンテナイメージはdigestも固定する。
- 可変の `latest` タグは使用しない。

#### サービス間の接続とDBの準備

各サービスは以下の接続先を使用する。

- ローカルAPIからPostgreSQLへは `127.0.0.1:5432` で接続する。
- ローカルBFFからRedisへは `127.0.0.1:6379` で接続する。
- ローカルBFFからAPIへは従来どおり `localhost:8080` で接続する。
- ZAPからAPIへは `host.docker.internal:8080` で接続する。
- ZAPからBFFへは `host.docker.internal:3000` で接続する。
- DBの準備には既存のmigrationと蔵書seedを再利用する。

#### ZAPの接続確認

ZAPの接続は以下の順序で確認する。

1. ローカル起動したAPI・BFFへの接続、ログイン、操作を確認する。
2. 問題がある場合は、接続先とホスト名などの設定を調整する。
3. 調整が複雑になる場合は、API・BFFのコンテナ化を検討する。

設定の調整では以下の条件を維持する。

- 認証とOrigin検証を無効化しない。
- 正常なログインと操作を受け付ける。
- 不正なOriginからの操作を拒否する。

#### 終了コードと検査の続行

各チェックと共通の入口は、以下の終了コードを使用する。

- `0`は検査完了かつ対応が必要な指摘なしを表す。
- `1`は検査完了かつ対応が必要な指摘ありを表す。
- `2`は検査自体の失敗または未完了を表す。

グループ全体の終了コードは、以下の優先順で決める。

- 失敗・未完了のチェックが一つでもあれば `2` とする。
- 失敗・未完了がなく、対応が必要な指摘があれば `1` とする。
- 全チェックが完了し、対応が必要な指摘がなければ `0` とする。

検査の続行は以下の方針とする。

- 指摘や実行失敗があっても、実行可能な残りの検査を続行する。
- 前提となる環境や処理の失敗で実行できない検査は、未完了として扱う。
- 起動失敗時に既存サービスを代用しない。

#### 検査結果と対応事項

検査結果は以下の方針で扱う。

- 各チェックの結果とグループ全体の判定を端末に表示する。
- 検査結果ファイルの保存を必須にしない。
- 詳細なレポートが必要な場合だけ、一時ファイルへ出力する。
- 検査結果ファイルはGit管理しない。
- 資格情報や生の通信内容を含む出力は、そのまま共有しない。

対応事項は以下の方法で管理する。

- 検出した対応事項は既存のTODO運用に従って記載する。
- 対応を保留する場合も、判断と残る対応をTODOに記載する。
- TODOへの記載や対応の保留を理由に、終了コードを成功へ変更しない。
- 検査が完了し、対応が必要な指摘が残っていれば `1` とする。
- 終了コードの判定でTODOの内容を解析しない。

#### 実行基盤の検証

実行基盤は以下の条件で検証する。

- 開発環境が起動中でも、既存のプロセスとDBを変更しない。
- 中断と起動失敗の後も、検査環境だけを片付ける。
- 情報更新失敗、ツール異常、認証失敗、タイムアウトを区別する。
- 安全な専用fixtureで検出ルールの動作を確認する。
- 実装時は変更対象に対応する必須品質検査を行う。
- 文書変更時は `python3 scripts/check-docs.py` を実行する。

### 依存関係の既知脆弱性検査

依存関係は以下の方法で確認する。

- フロントエンドは既存のnpm auditを活用する。
- JavaはTrivyを使用する。
- Trivyの公式イメージはGHCRの `ghcr.io/aquasecurity/trivy` から取得する。
- Gradleタスクで解決済みの依存JARを検査用ディレクトリへ集める。
- 実行用、テスト用、コード生成用の依存関係を抽出対象とする。
- 抽出対象のGradle構成を明示する。
- 抽出先は実行ごとに同期し、過去の依存JARを残さない。
- 抽出したディレクトリを読み取り専用でTrivyへ渡す。
- 依存JARの抽出だけを目的としたアプリのコンパイルは行わない。
- 検出した脆弱性はアプリへの影響と到達可能性を評価する。

依存JARの自動検査で確認できない範囲は、以下のように扱う。

- Gradle本体、JDK、ビルドプラグインは、公式情報で別途確認する。
- Trivyが識別できないJARを、問題なしと扱わない。
- 確認できた範囲と検査の限界を明示する。

Trivyは以下の理由と利用条件で採用する。

- JAR、コンテナ、秘密情報を共通の仕組みで確認できる点を利点とする。
- Java依存関係の認識範囲を確認する。
- 2026年3月の侵害に対する復旧対策の公式報告を踏まえて採用する。
- 採用版と配布元を公式情報で評価する。
- 版やdigestの固定だけで供給元の安全性確認を代替しない。

Trivyの配布物は以下の方法で検証する。

- 導入・更新時に採用版の配布体制と関連するアドバイザリを確認する。
- Trivy公式のコンテナ署名検証手順に従い、Cosignで署名を検証する。
- Cosignは公式イメージ `ghcr.io/sigstore/cosign/cosign` をComposeから実行する。
- CosignのCLIはローカルにインストールしない。
- 期待する署名者と発行元を、公式手順に従って照合する。
- GHCR上の採用対象をdigestで指定して検証する。
- 検証したdigestをComposeへ固定し、通常の検査で使用する。
- 検証に失敗した場合は、そのイメージを採用・実行しない。

Trivyに渡すファイルと権限は以下の範囲に限定する。

- 検査対象ファイルは読み取り専用で渡す。
- 書き込み先はキャッシュと一時出力先に限定する。
- SSH鍵、クラウド資格情報、個人の設定ファイルは渡さない。
- 特権モードは使用しない。
- Dockerソケットは共有しない。
- コンテナイメージはレジストリから直接取得して検査する。

### コンテナイメージの既知脆弱性検査

コンテナは以下の方法で確認する。

- PostgreSQLとRedisで使用するイメージを検査する。
- 検査ツールはTrivyを使用する。
- 利用条件は依存関係検査と共通にする。

### ソースコードの静的検査

静的検査は以下の方法で実施する。

- Semgrep CEを使用する。
- 初期はSemgrepとコミュニティが管理する既存の公開ルールを使用する。
- CEで実行でき、使用言語と実装に対応するルールを選ぶ。
- 導入時点のルール集のコミットを固定する。
- 独自ルールは、既存ルールの不足が分かった段階で追加する。

ルールは以下の範囲から選ぶ。

- KotlinのAPIはSQL、コマンド実行、ファイル操作、暗号、TLSを対象とする。
- TypeScriptのBFFはコマンド実行、外部通信、ファイル操作を対象とする。
- Reactは危険なHTML描画などのXSS対策を対象とする。

検査の限界は以下の方法で補う。

- 単一関数内という解析制限を考慮する。
- ルールが扱わないコードはレビューする。
- 複数の関数やファイルを通る認証・認可はシナリオテストでも確認する。
- 検出がないことを、脆弱性がないことと同一視しない。

#### 参考資料

対応範囲は以下を参照する。

- [Semgrep CEの対応言語と解析制限](https://docs.semgrep.dev/semgrep-ce-languages)
- [Semgrepとコミュニティの公開ルール集](https://github.com/semgrep/semgrep-rules)

### 秘密情報検査

秘密情報は以下の方法で確認する。

- Trivyを使用する。
- 現在のGit管理対象ファイルを検査する。
- 利用条件は依存関係検査と共通にする。

#### 参考資料

検査機能は以下を参照する。

- [Trivyの秘密情報検査](https://trivy.dev/docs/dev/scanner/secret/)

### 起動したアプリの動的検査

動的検査は以下の方法で実施する。

- ZAPを使用する。
- 未認証状態と認証済み状態の双方を検査する。
- BFFの画面とAPIを対象にする。
- 認証成功と対象画面・APIへの到達を確認する。
- API検査にはOpenAPIを利用する案とする。
- 検査専用設定と通常の公開設定を区別する。
- 受動検査の後に、攻撃用入力を送る能動検査を行う。
- 業務上の認可不備はシナリオテストで補う。

ZAPの検査対象URLは以下の範囲に限定する。

- BFFはトップ、利用登録、ログイン、蔵書検索・予約の画面を対象にする。
- APIはOpenAPIに記載された実装済みの業務エンドポイントを対象にする。
- 管理系エンドポイントは初期のZAP検査対象から除外する。
- OpenAPIの取得先は検査定義の読み込みに使用する。
- 外部サイトへ検査を広げず、検査用に起動したBFFとAPIだけを対象にする。

認証済み検査は以下の手順で試す。

1. 検査用の合成メールアドレスとパスワードを用意する。
2. ZAPのブラウザ操作またはスクリプトで登録画面を操作し、検査用ユーザーを作成する。
3. BFFは同じ資格情報でログインし、セッションCookieを使用する。
4. APIは同じ資格情報でログインし、返されたBearerを使用する。
5. 認証成功と保護対象への到達を確認して検査する。

認証処理は以下の条件で実装する。

- ユーザー作成は検査の準備処理として行う。
- 再認証時は既存の検査用ユーザーでログインする。
- 検査中も認証状態が維持されていることを確認する。
- 認証失敗を、認証済み検査の成功として扱わない。
- 資格情報、Cookie、Bearerを端末や共有用の出力に表示しない。
- 登録・ログインの具体的な操作手順は実装時に動作確認する。

アドオンは以下の方針で導入する。

- 合意済みの検査手順を実行するための最小限に絞る。
- 採用イメージに同梱された機能を優先する。
- 自動実行、認証、画面探索、OpenAPI読み込みに不足する機能だけを追加する。
- 不要な独自アドオンや実験的な検査ルールは追加しない。
- 実際の検査で不足が分かった場合に追加する。
- 導入したアドオンの版を固定する。

能動検査のルールは以下の方針で選ぶ。

- 初期は安定版の標準ルールを基本とする。
- Alpha・Betaのルールは追加しない。
- 独自ルールは作成しない。
- 負荷と実行時間を実測し、過剰になるルールを調整する。

実行時間と負荷は以下の上限から始める。

- 準備とビルドを除く動的検査全体を、最大30分とする。
- 同時に送るリクエスト数は1とする。
- 時間上限に達した場合は未完了とし、終了コードを `2` とする。
- 初回の実測後に、検査範囲と上限を調整する。

### アプリ固有の漏洩シナリオテスト

シナリオテストは以下の方法で整備する。

- 認可とトークン失効はAPIテストで確認する。
- ブラウザでの確認が必要な項目は、既存のPlaywright E2Eを活用する。
- 既存テストを確認し、不足を追加する。
- 既存の受け入れ条件と実装済み機能に合わせる。

以下のシナリオを確認する。

- 未認証状態で保護対象の情報・操作へアクセスする。
- 他利用者として操作しようとする。
- Cookieを改ざんする。
- セッション固定化を試みる。
- 期限切れセッションを再利用する。
- ログアウト後にセッションやトークンを再利用する。
- CSRFとXSSの代表的な異常系を試す。
- ブラウザ、応答、ログへのBearer、パスワード、個人情報の露出を確認する。

### コードと設定のレビュー

自動検査で補えない点を以下の方法で確認する。

- コードと設定をチェックリストでレビューする。
- 静的検査の対象外と、関数やファイルをまたぐ認証・認可を確認する。
- 新しい攻撃への対応で自動検査できない点をレビュー項目へ追加する。
- 初回のレビュー結果を確認する。
