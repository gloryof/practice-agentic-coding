# 運用・非機能ベースライン

## 目的
- 本文書は、アーキテクチャ、セキュリティ、DB の設計またはレビューで共通して使用する運用・非機能前提の正本である。
- 練習用アプリケーションとしての現在状態と、実践的な設計レビューに使用する仮想本番の目標を区別する。
- 通常の機能実装、文言修正、テストのみの変更では必須参照としない。

## 責務境界
- ビジョン、対象利用者、単一館というプロダクト前提は `product/product-foundation.md` を正本とする。
- ユーザー向け振る舞い、業務データの意味、ドメイン制約は `product/domain-context` を正本とする。
- API の構造、ログ、永続化などの実装規則は `api/docs/backend-guidelines.md` を入口とする。
- フロントエンドの構造、ツールチェーン、実行時設定、ビルドなどの実装規則は `frontend/docs/frontend-guidelines.md` を入口とする。
- 本文書は横断的な目標、制約、決定状態を扱い、製品固有の構成、詳細な作業手順、秘密値、連絡先は扱わない。
- 将来デプロイする場合の具体的な基盤選定は ADR、障害対応や復元の具体的な手順はランブックで管理する。

## 決定状態
| 状態 | 意味 |
|---|---|
| 確定 | 採用済みの前提または設計目標 |
| 現状確認 | リポジトリから確認できる現在の実装状態。将来の方式を拘束しない |
| 計画 | 実装予定だが具体的な方式が決まっていない事項 |
| 未決定 | 推測で補わず、判断トリガーに到達するまで保留する事項 |
| タスク固有 | 対象変更の設計またはレビューで依頼側が補う事項 |
| 対象外 | 対象外とする理由を説明できる事項 |

未決定事項は、単なる `TBD` ではなく、判断トリガーと影響範囲を併記する。現状未実装であることと、方針が未決定であることを混同しない。

## システムコンテキスト
| 項目 | 状態 | 前提 |
|---|---|---|
| 利用目的 | 確定 | デプロイせず、実利用者データを扱わない練習用アプリケーション |
| 対象館 | 確定 | 単一のコミュニティ図書館 |
| サーバーサイド | 現状確認 | ローカルで動作する単一の Spring Boot API |
| データベース | 現状確認 | ローカルおよびテスト用の PostgreSQL 16。現在は全コンテキストが単一DBを共有する |
| フロントエンド | 計画 | 図書館利用者向けフロントエンドを追加する予定 |
| フロントエンド方式 | 確定 | React、React Router Framework Mode、Vite、TypeScript strict による CSR SPA。実行時SSRは使用しない |
| フロントエンドAPI接続 | 確定 | ブラウザ標準の `fetch` を共通境界から使用し、ローカルではVite開発プロキシを経由して別起動のSpring Boot APIへ接続する。型同期、認証、CORS、エラー契約は後続設計で決定する |
| フロントエンド設定 | 確定 | 起動前に公開設定JSONを取得・検証する。同一ビルド成果物を環境間で移送可能とし、秘密値は含めない |
| フロントエンドビルド・配布 | 確定 | Node.js 24 LTSとnpmで独立した静的成果物を生成する。Spring Bootへの同梱と静的配信だけを目的とする常駐Node.jsサーバーは採用しない |
| フロントエンドホスティング | 対象外 | 現在はデプロイしない。デプロイ方針を変更する場合に静的配信基盤、同一Origin化、リリース、ロールバックを決定する |
| フロントエンドテレメトリ | 対象外 | 現在は外部SDKと送信基盤を導入しない。デプロイまたは実利用を開始する場合に再評価する |
| 外部連携 | 現状確認 | 本番相当の外部サービス依存は確認できない |
| 運用担当 | 確定 | リポジトリ管理者が保守する。常時オンコールと外部向けサポートは設けない |

## レビュー入力の分担
| レビュー | 本文書で確認する入力 | タスク固有で補う入力 |
|---|---|---|
| アーキテクチャ | 利用規模、性能、可用性、復旧、運用、可観測性、コストの前提 | 対象構成、重要な利用者フロー、依存関係、データフロー、障害ドメイン |
| セキュリティ | データ分類、保持、保護、秘密情報、インシデント対応の前提 | 信頼境界、対象コード・設定、脅威、悪用シナリオ、追加のコンプライアンス要件 |
| DBA | データ規模、性能、バックアップ、RPO/RTO、保持、DB運用責任の前提 | 対象スキーマ、クエリ、インデックス、マイグレーション、ロールアウト計画 |

本文書で未決定とした事項が対象タスクの判断に必要な場合、レビュー担当は推測せず、判断トリガーへの到達有無と必要な決定を指摘する。

## 利用規模と容量
以下は小規模な単一館を想定した仮想本番の設計目標であり、現在の実績値ではない。

| 項目 | 設計目標 |
|---|---:|
| 登録利用者 | 10,000人 |
| 書誌 | 50,000件 |
| 蔵書 | 100,000件 |
| 予約 | 10,000件 |
| 同時利用 | 50人 |
| APIピーク負荷 | 10 RPS |

- 性能または容量に影響する変更では、上記データ量の2倍までを余力確認の基準とする。
- 実データの増加率は未決定とする。デプロイ方針を変更する場合、または容量対策を設計する場合に決定する。

## 性能目標
### API
| 処理 | p95 | p99 |
|---|---:|---:|
| 蔵書検索 | 500ミリ秒以内 | 1秒以内 |
| 利用者登録、ログイン、予約 | 1秒以内 | 2秒以内 |

- サーバーエラー率は、意図した障害試験を除き1%未満とする。入力不備や認証失敗など、契約どおりの4xx応答はサーバーエラー率に含めない。
- ローカル性能検証では、対象データ量、同時利用数、リクエスト構成、ウォームアップ時間、5分以上の計測時間、CPU、メモリ、Java、PostgreSQLの条件を記録する。
- APIピーク負荷10 RPSと同時利用50人の条件で目標値を評価する。性能に影響する変更では、再現可能な試験方法と結果をタスク固有の検証記録に残す。

### フロントエンド
- API性能だけで利用者が体感する画面性能を満たしたとは判断しない。
- 画面表示、主要操作の応答、配信資産量に関する目標は、フロントエンドの品質・非機能要件を決める設計タスクで定義する。
- フロントエンド追加後は、登録、ログイン、蔵書検索、予約の主要フローをエンドツーエンドで計測する。

## 可用性、デプロイ、復旧
以下は仮想本番を想定した設計レビュー上の目標であり、現在の稼働保証ではない。

| 項目 | 設計目標 |
|---|---|
| 主要利用フローの可用性 | 月間99.5%以上 |
| 主要障害領域の一次特定 | 検知から10分以内 |
| アプリケーションのロールバック | 発動判断から30分以内 |
| RTO | 4時間以内 |
| RPO | 24時間以内 |

- 現在はデプロイしないため、デプロイ、段階的リリース、ロールバック、メンテナンス時間帯の実手順は対象外とする。
- デプロイする方針へ変更する場合は、フロントエンド、API、DBの障害ドメイン、リリース順序、ロールバックまたはロールフォワードの条件を実装開始前に決定する。
- 本番DBの構成、高可用化、レプリケーション、PITRは未決定とする。RPOを24時間未満へ短縮する場合、または実利用者データを扱う場合に再評価する。

## 可観測性と障害対応
- 現在のAPIはhealth、info、metricsを公開対象に設定し、`traceId`をリクエスト、レスポンス、ログで追跡できる。
- prometheusも公開対象名に含まれるが、Prometheus registryは未導入であり、利用可能なエンドポイントとは扱わない。ログ形式には`spanId`欄があるが、分散トレース実装は確認できない。
- 仮想本番では、リクエスト数、p95/p99、4xx/5xx、JVM、DB接続プール、低速クエリ、バックアップ結果を観測対象とする。
- 次の状態をアラートの設計基準とする。
  - ヘルスチェックが5分継続して失敗する。
  - 5分間の5xx率が5%を超える。
  - 10分間継続して性能目標を超える。
  - DB接続プール使用率が10分間80%を超える。
  - バックアップが失敗または未完了になる、もしくは最新の復元可能点が24時間を超える。
- フロントエンドをデプロイする場合または実利用を開始する場合は、画面エラー、主要操作の成功率、画面性能、APIまで伝播する相関識別子を観測対象に加える。
- 障害対応の責任者はリポジトリ管理者とし、練習では障害シナリオごとに10分以内の一次切り分け可否を確認する。
- デプロイする方針へ変更する場合は、通知経路、重大度、一次対応時間、エスカレーション、ランブックを外部公開前に決定する。

## データ分類と保護
| 分類 | 対象 | 最低限の扱い |
|---|---|---|
| 公開 | 明示的に公開対象と決定した情報、ブラウザへ渡すAPI Base URLなどの実行時設定 | 公開範囲と完全性を維持する。分類だけでアクセス許可を与えない。秘密値を含めない |
| 内部 | 書誌・蔵書・予約、利用者ID、ブラウザへ渡さない非秘密の構成情報、集約済みメトリクス | 不要な外部公開を避け、アクセスを目的に必要な範囲へ限定する |
| 個人情報 | メールアドレス | ログへ出力せず、保存・参照を必要最小限にする |
| 認証秘密 | 平文パスワード、アクセストークン、パスワードハッシュ、DB・サービス資格情報、暗号鍵 | ソース、文書、ログへ値を記録せず、最小権限と失効・ローテーション可能性を確保する |

- 個人情報は現時点でメールアドレスのみとする。
- 利用者IDや予約情報は内部データだが、メールアドレスと結合可能な状態では個人情報と同等の保護を適用する。
- ログ、ブラウザ保存領域、トレース、エクスポート、バックアップは、含まれる元データの最も厳しい分類を継承する。
- フロントエンドの実行時設定はブラウザから閲覧可能であるため、公開可能な非秘密情報だけを含める。
- 平文パスワードは保持しない。ローカル検証では合成メールアドレスを使用する。
- フロントエンドでの認証情報の保持方式は、認証方式と脅威モデルを決める設計タスクで決定する。
- デプロイする方針へ変更する場合は、転送中と保存時の保護、秘密情報管理、最小権限、資格情報侵害時の失効、依存関係の脆弱性対応を外部公開前に決定する。

## 保持、バックアップ、DB運用
| 項目 | 前提 |
|---|---|
| ローカルデータ | テスト用であり、作業または検証の後に破棄できる |
| 個人情報 | アカウントが存在する間は保持する。アカウント削除を設計する場合、削除条件と期限をプロダクト仕様で決定する |
| ログ | 仮想本番では30日保持を設計目標とする。メールアドレスと認証秘密は含めない |
| バックアップ | 仮想本番では日次取得、30日保持、暗号化とアクセス制御を設計目標とし、最新の復元可能点を常に24時間以内に維持する |
| 復元試験 | 仮想本番では四半期ごとに実施し、RPO/RTO、Flyway履歴、制約、主要利用フローを確認する |

- 現在のローカルDBはバックアップ対象外であり、バックアップや復元試験が実装済みであることを意味しない。
- 本番マイグレーションの実行主体、事前バックアップ、ロールバックまたはロールフォワード、メンテナンス時間帯は未決定とする。デプロイ方針を変更する場合に決定する。
- 破壊的なマイグレーションまたは大規模データ変更を設計する場合は、デプロイ有無にかかわらず、対象データ量、復旧方法、リハーサル、合否基準をタスク固有情報として明示する。

## コスト
- 現在はデプロイしないため、継続的な本番インフラ費用は発生させない。
- 設計レビューでは、compute、storage、network、observabilityを主要コスト要因として扱い、現在規模に対して単純な構成を優先する。
- デプロイする方針へ変更する場合は、基盤選定前に月額上限、増加トリガー、コスト監視、見直し周期を決定する。

## ローカル検証と更新条件
- 性能目標は、自動または反復可能なローカル試験で検証できる形にする。試験ツールの選択と試験データの準備は、性能に影響するタスクで決定する。
- 可用性、アラート、バックアップ、復元は未デプロイ環境で実績値を測定できないため、設計レビュー、障害訓練、復元リハーサルによって確認する。
- フロントエンド実装設計、デプロイ方針の変更、実利用者データの利用、利用規模の変更、SLOの変更、データ保持方針の変更、運用体制の変更、バックアップ方式の採用時は、同じ変更で本文書を更新する。
- 判断トリガーに到達しても必要事項を決定または実装できない場合は、`task/todo/TEMPLATE.md`に従って未解決事項を起票する。
