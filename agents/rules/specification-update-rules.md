# 仕様更新ルール

## 目的
- 仕様判断と実装変更に伴って更新する正本を一意に判断できるようにする。
- 仕様、ユーザーストーリー、索引の不整合を同じ変更内で防ぐ。
- 本文書を仕様更新ルールの単一の正本とする。

## 適用条件
- 仕様の作成、更新、Q&A を行う場合に適用する。
- 機能追加、バグ修正、リファクタリング、実装設計によって既存仕様が変わる場合に適用する。
- 文言修正や構成整理だけで仕様の意味や索引情報が変わらない場合、正本の追加更新は不要とする。

## 更新前の確認
- 仕様判断または実装着手前に、`product/domain-context/README.md` の探索規約に従って関連するドメイン仕様を特定する。
- `product/product-foundation.md`、関連する `task/user-stories`、特定した `product/domain-context` を確認する。

## 正本と更新条件

| 変更対象 | 更新する正本 | 更新条件と責務 |
|---|---|---|
| ビジョン、ミッション、プロダクト全体の前提 | `product/product-foundation.md` | これらの意味または制約を決定・変更した担当者が、同じ変更で更新する。 |
| ユーザー価値、ユースケースの入出力・制約・失敗条件・処理フロー | `product/domain-context` の該当ユースケース | 振る舞いを決定・変更した担当者が、同じ変更で更新する。 |
| ドメインモデル、ドメインイベント | `product/domain-context` の該当モデル・イベント | モデルまたはイベントの意味・制約・属性・発生条件を決定・変更した担当者が、同じ変更で更新する。 |
| ドメイン制約 | `product/domain-context` の該当制約 | 複数の状態やモデルを組み合わせて業務上の可否を決める条件、その入力、判定結果を決定・変更した担当者が、同じ変更で更新する。 |
| ユーザーストーリー、受け入れ条件 | `task/user-stories` の該当ストーリー | ユーザー価値または受け入れ条件を決定・変更した担当者が、同じ変更で更新する。 |
| ユーザーストーリーの追加、名称・状態・優先順位の変更 | `task/user-stories/index.md` | 索引の表示内容が変わる変更を行った担当者が、同じ変更で更新する。 |
| ユビキタス言語の追加、変更、削除 | `product/ubiquitous/terms.md` と該当する用語定義 | `product/ubiquitous/governance.md` の承認・変更手順に従い、同じ変更で索引と定義を更新する。 |
| ドメインコンテキストの追加、名称変更、実装基底パッケージの変更 | `product/domain-context/README.md` の対応表 | 対応関係を変更した担当者が、同じ変更で更新する。 |

## 新規文書と整合性
- 新しいコンテキスト、ユースケース、モデル、イベント、制約は、`product/domain-context/README.md` の構造・命名・リンク規約に従って配置する。
- ユーザーストーリーとドメイン仕様が食い違う場合は、意図を確認し、どちらか一方だけでなく同じ変更で整合させる。

## 完了確認
- 変更した仕様に対応する正本が、同じ変更に含まれていることを確認する。
- 新規作成または更新した文書の相対リンクが存在することを確認する。
- ドキュメント変更後に `./scripts/check-no-local-paths.sh` を実行する。
