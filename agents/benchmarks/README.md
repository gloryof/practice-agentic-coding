# Agentワークフローベンチマーク

## 目的
- Agentワークフロー改善前後の作業着手前コンテキストと計画品質を、同じ入力と評価基準で比較できるようにする。
- 必要なガードレールを維持したまま、不要・重複コンテキストを削減できたか判断する。
- 日常的な学習では短いフィードバックサイクルを優先し、必要な節目では選択したシナリオを成果物作成・レビュー・検証まで実行する。
- 実トークンを取得できない環境でも、計測可能な代替指標を実トークンと混同せずに残す。

## ベンチマーク構成

| ID | 系列 | シナリオ | 主な計測対象 | 状態 |
|---|---|---|---|---|
| `01-code-investigation` | 軽量 | コード調査 | 読み取り専用調査のルーティングとコード探索 | 定義済み |
| `02-minor-change` | 軽量 | 軽微変更 | 小規模変更で省略できる文書、レビュー、検証 | 定義済み |
| `03-user-story-creation` | 主系列 | ユーザーストーリー作成 | `po-story`、プロダクト前提、受け入れ条件 | 定義済み |
| `04-domain-model-specification` | 主系列 | ドメインモデル仕様作成 | `po-spec`、ドメイン探索、仕様正本の更新 | 定義済み |
| `05-api-implementation` | 主系列 | API実装 | 固定仕様からのサーバー実装、レビュー、検証 | 定義済み |
| `06-frontend-implementation` | 主系列 | フロントエンド実装 | 固定仕様からの画面・BFF実装、レビュー、検証 | 定義済み |
| `07-api-architecture-policy` | 技術方針文書 | APIアーキテクチャ方針変更 | 設計判断、非機能前提、設計方針レビュー | 定義済み |
| `08-frontend-architecture-policy` | 技術方針文書 | フロントエンドアーキテクチャ方針変更 | 境界設計、非機能前提、条件付き設計方針レビュー | 定義済み |

- 主系列の後段には、直前のベンチマーク実行で生成した成果物を渡さない。シナリオで固定したユーザーストーリーまたは仕様スナップショットを使用し、実行ごとの生成差分を後段へ伝播させない。
- シナリオ内の固定仕様や業務判断はベンチマーク入力であり、プロダクト仕様の正本へ採用済みであることを意味しない。`pre-work`では正本へ反映せず、`full-run`の変更は隔離した一時worktree内だけで扱う。
- 技術方針文書系列は、文言修正や意味を変えない構成整理ではなく、設計方針を意味のある形で変更する依頼とする。
- 技術方針文書系列では、対象コミット時点の実装フローに基づいて分類、適用スキル、レビューを選択し、その結果と根拠を記録する。

## 実行モード

後続比較との互換性を維持するため、実行モードと実行区分は英語表記のまま使用する。

| 実行モード | 対象 | 終了条件 |
|---|---|---|
| `pre-work` | 8シナリオすべての標準計測 | リポジトリを変更せず、シナリオごとの着手可能な成果物または計画を完成させる。 |
| `full-run` | 8シナリオすべての節目計測 | 固定入力が求める成果物を完成し、適用されるレビュー、検証、最終報告まで完了する。 |

| 実行区分 | 用途 |
|---|---|
| `pilot` | 初回試運転、手順検証、または未コミット変更を含む計測。正式比較には使用しない。 |
| `official` | 検証済み手順とクリーンな作業ツリーによる正式比較候補。 |

- 基準値の確定時と、主要なワークフロー改善を完了した後に、比較目的に応じて一つ以上のシナリオを`full-run`で実行する。全工程の比較が必要な場合は全8シナリオを実行できる。
- `pre-work`と`full-run`の値は別々に集計し、一つの総量へ混在させない。
- `pre-work`で予定したスキル、レビュー、検証と、`full-run`で実際に必要になったものの差分を記録する。

## 作業着手前の成果物

| シナリオ | `pre-work`の終了成果物 |
|---|---|
| コード調査 | 根拠と不明点を含む調査結果 |
| 軽微変更 | 変更対象、変更内容、検証方法を確定した作業計画 |
| ユーザーストーリー作成 | 必須出力契約を満たすユーザーストーリー案 |
| ドメインモデル仕様作成 | 正本へ反映可能なドメインモデル仕様案 |
| API実装 | 対象、契約、データフロー、失敗条件、テスト、レビューを確定した実装計画 |
| フロントエンド実装 | 画面、BFF・Client境界、UI状態、テスト、レビューを確定した実装計画 |
| APIアーキテクチャ方針変更 | 方針案、影響範囲、必要レビュー、整合確認を確定した変更計画 |
| フロントエンドアーキテクチャ方針変更 | 方針案、境界への影響、必要レビュー、整合確認を確定した変更計画 |

- 作業計画は実装担当が追加判断せずに着手できる具体性を持たせる。
- ユーザーストーリー案とドメインモデル仕様案はAgentの回答として完成させるが、リポジトリへは書き込まない。
- `pre-work`ではコード、仕様文書、TODO、設定、生成物を変更しない。

## 完全実行の成果物

| シナリオ | `full-run`の終了成果物 |
|---|---|
| コード調査 | ファイルを変更せず、根拠と不明点を含む調査結果を完成し、適用可能な読み取り専用検証を終える。 |
| 軽微変更 | 指定されたリファクタリング、適用されるレビュー、検証を完了する。 |
| ユーザーストーリー作成 | ユーザーストーリーの正本と必要な索引を更新し、適用されるレビューと文書検証を完了する。 |
| ドメインモデル仕様作成 | 関連する仕様正本を整合して更新し、適用されるレビューと文書検証を完了する。 |
| API実装 | API契約から実装、レビュー、テスト、必要なE2Eまでを完了する。 |
| フロントエンド実装 | 画面とBFF境界の実装、レビュー、テスト、必要なE2Eまでを完了する。 |
| APIアーキテクチャ方針変更 | 技術方針の正本と必要なリンクを更新し、適用される設計レビューと整合確認を完了する。 |
| フロントエンドアーキテクチャ方針変更 | 技術方針の正本と必要なリンクを更新し、適用される設計レビューと整合確認を完了する。 |

- `full-run`でも固定入力と対象コミット時点の適用規約を優先し、適用されないファイル変更、レビュー、検証を実行した体裁にしない。該当しない工程は理由とともに`not_applicable`として記録する。
- 各シナリオは同じ対象コミットから作成した独立worktreeで実行し、他シナリオの成果物を入力または前提にしない。

## 成果物
- シナリオの固定入力は`agents/benchmarks/scenarios/<scenario-id>.md`に保存する。
- シナリオ本文へ含められない固定スナップショットが必要になった場合だけ、`agents/benchmarks/fixtures/<scenario-id>/`を追加する。
- 実行結果は[結果テンプレート](RESULT_TEMPLATE.md)を使用し、`agents/benchmarks/baselines/<baseline-id>/<scenario-id>.md`に保存する。
- `<baseline-id>`は計測日と対象コミットを識別できる名前にする。文書内には対象コミットの完全なGit SHAを別途記録する。
- 初回試運転または手順上の欠陥が見つかった結果は削除せず、正式基準値への採否を`不採用`として理由を残す。不採用結果を含むBaseline IDは次回実行で再利用しない。

## 役割の分離
- 計測者は実行条件の固定、作業Agentの起動、参照履歴の記録、事後分類、結果保存を担当する。
- 作業Agentは固定入力に対する作業だけを担当する。
- 結果テンプレートのMain Agentは作業Agentを指す。計測Coordinator自身のコンテキストは計測値へ含めない。
- 作業Agentには本書で実行モードに対応する「固定の計測報告契約」とシナリオファイルの本文だけを渡し、本書そのもの、結果テンプレート、過去の実行結果を渡さない。
- レビュー担当を使用するシナリオでは、Main Agentとレビュー担当の参照履歴と使用量を分けて記録する。

## 実行条件
1. 対象コミットを固定し、完全なGit SHAと作業ツリーの状態を記録する。
2. モデル、reasoning設定、利用可能なツール、実行環境を固定して記録する。
3. シナリオごとに会話履歴のない新規セッションを使用する。
4. 実行モードを記録し、シナリオファイルの内容を変更せずに作業Agentへ渡して開始時刻を記録する。
5. `pre-work`ではリポジトリを変更しない。`full-run`では対象コミットから隔離した一時worktreeを使用し、ベンチマーク用の変更を通常の作業ツリーへ混入させない。
6. 作業終了時に終了時刻、成果物、検証結果、残リスクを記録する。
7. 実行後に固定入力と対象コミット時点の適用規約へ照らし、成果物、ガードレール、完了条件の見落としを評価する。

## Skillによる実行

リポジトリの新規セッションを開き、次のように依頼する。

```text
コンテキストのベンチマークを取りたい。
```

`.codex/skills/agent-workflow-benchmark/SKILL.md`が計測Coordinatorとして自動適用され、既定では次を行う。

1. 実行対象が未指定なら、`all`またはシナリオIDの指定を求める。
2. 同じ実行条件の未完了Baseline IDを再利用する。該当するBaseline IDがなければ新しく作る。
3. 選択した実行モードとして実行条件を記録する。指定がなければ`pre-work`とする。
4. 選択したシナリオをID順に、会話履歴を継承しない別々の作業Agentで実行する。
5. 各作業Agentへ実行モードに対応する固定の計測報告契約と対象シナリオ本文だけを渡す。
6. 選択した全作業Agentの終了後、結果テンプレートへ転記・分類し、`agents/benchmarks/baselines/<baseline-id>/<scenario-id>.md`へまとめて保存する。

- `all`または「全件」を指定すると、同じBaseline IDで結果が未保存の定義済みシナリオをすべて実行する。
- 一つ以上のシナリオIDを指定すると、指定したシナリオだけを実行する。
- 既存結果は上書きしない。選択したBaseline IDで実行済みのシナリオはスキップし、再実行時は新しいBaseline IDを使用する。
- `full-run`でも`all`または一つ以上のシナリオIDを指定できる。
- シナリオID、Baseline ID、実行モードを指定したい場合は、最初の依頼に追記できる。
- 未コミット変更がある実行は`pilot`として保存し、正式な基準値と区別する。
- 初回試運転または手順検証を目的とする実行も、作業ツリーがクリーンでも`pilot`として扱う。
- 自動適用されない場合は、`$agent-workflow-benchmark`を明示して同じ依頼を行う。

全シナリオを実行する例:

```text
コンテキストのベンチマークを取りたい。全件実行して。
```

全シナリオを`full-run`で実行する例:

```text
コンテキストのベンチマークを取りたい。full-runで全件実行して。
```

シナリオを選択する例:

```text
コンテキストのベンチマークを取りたい。02-minor-changeと07-api-architecture-policyを実行して。
```

## `pre-work`用の固定計測報告契約

計測Coordinatorは、次の本文とシナリオ本文だけを作業Agentへ渡す。表現や項目を実行ごとに変更しない。

```text
あなたは固定入力の具体的な作業だけを担当する作業Agentです。シナリオ選択、別Agentの起動、ベンチマーク結果ファイルの作成は行わないでください。

実行モードはpre-workです。リポジトリのファイル変更、レビュー担当の起動、テストや検証コマンドの実行は行わず、固定入力に対応するpre-work終了成果物までを完成させてください。既存テストコードは根拠として参照できます。

対象コミット、Git状態、モデル、reasoning設定、実行環境、開始・終了日時は計測Coordinatorが記録するため、取得しないでください。

通常の成果物に続けて「参照履歴報告」を出力してください。参照履歴報告には次を含めてください。

- 適用した依頼分類、対象領域、仕様影響、フローと、その判断根拠。
- 実際に呼び出したスキル、その区間、理由、実行結果。呼び出していない場合は「なし」と理由。
- 参照したリポジトリ文書とコードの相対パス、取得範囲または取得行数、参照回数、参照理由。
- 実行した検索とコマンド、その出力から得た判断。
- 作業着手後に予定するスキル、レビュー、検証と、それぞれの適用条件。
- 不明点、取得できない計測値、成果物の残リスク。

観測できない値は推測せず「not_available」と理由を記載してください。
```

固定契約は計測可能性と作業Agentの境界を確保するための共通入力であり、シナリオ固有のフロー、スキル、参照文書、期待結果を示さない。

## `full-run`用の固定計測報告契約

計測Coordinatorは、いずれかのシナリオを`full-run`で実行する場合、次の本文とシナリオ本文だけを作業Agentへ渡す。表現や項目を実行ごとに変更しない。

```text
あなたは固定入力の具体的な作業だけを担当する作業Agentです。シナリオ選択、ベンチマーク結果ファイルの作成は行わないでください。

実行モードはfull-runです。計測Coordinatorが対象コミットから作成した隔離worktreeだけで、固定入力に対応する成果物の完成、必要なレビュー、検証、指摘反映、最終報告までを完了してください。固定入力がファイル変更を禁止している場合は変更せず、適用されない工程を理由とともに報告してください。

固定入力冒頭の`Scenario ID`を確認してください。隔離worktreeは`$TMPDIR/agent-workflow-benchmark-full-run/<Scenario ID>`です。最初に環境変数`TMPDIR`を展開して実体パスを確認し、その位置がGit worktreeとして登録されていることを確認してください。以後のファイル参照、変更、ステージング、レビュー、検証はすべてそのworktreeを作業ディレクトリとして実行してください。元の作業ツリー、ベンチマーク結果保存先、同じ固定ルート内の他のScenario IDのworktreeは変更しないでください。隔離worktreeを作成、移動、削除しないでください。

対象コミット、元の作業ツリーのGit状態、モデル、reasoning設定、実行環境、開始・終了日時は計測Coordinatorが記録するため、取得しないでください。隔離確認、成果物作成、レビュー、検証に必要なGit状態と差分は取得してください。

リポジトリの適用規約と固定入力に従って必要なスキルを使用してください。適用規約がレビュー担当を必須とする場合は、会話履歴を継承しないレビュー担当を起動し、隔離worktreeの変更だけをレビューさせてください。レビュー担当へも、参照した文書とコード、検索、コマンド、判断、不明点を報告させてください。

通常の最終報告に続けて「参照履歴報告」を出力してください。参照履歴報告には次を含めてください。

- 適用した依頼分類、対象領域、仕様影響、フローと、その判断根拠。
- 実際に呼び出したスキル、その区間、理由、実行結果。呼び出していない場合は「なし」と理由。
- Main Agentとレビュー担当を分けた、参照したリポジトリ文書とコードの相対パス、取得範囲または取得行数、参照回数、参照理由。
- Main Agentとレビュー担当を分けた、実行した検索とコマンド、その出力から得た判断。
- 実行したレビュー、検証、指摘反映と結果。適用しなかった候補は、その条件と理由。
- 変更したファイル、ステージング結果、未解決事項、取得できない計測値、成果物の残リスク。

観測できない値は推測せず「not_available」と理由を記載してください。
```

この固定契約は、隔離worktreeの場所を環境変数と固定入力内のScenario IDによる一定の表現に固定し、実行ごとのパス文字列を作業Agentの入力へ追加しない。計測Coordinatorは作業Agentの起動前に、選択した各シナリオについて同じ対象コミットから独立worktreeを作成し、全作業Agentの終了後に結果保存と後片付けを行う。

## 手動での試運転手順
1. 試運転前に対象コミットと作業ツリーの状態を記録する。
   ```shell
   git rev-parse HEAD
   git status --short
   ```
2. 使用するモデル、reasoning設定、利用可能なツール、開始日時を結果テンプレートへ記録する。
3. `full-run`の場合は、`$TMPDIR/agent-workflow-benchmark-full-run`が存在せず、その位置または配下がGit worktreeとして未登録であることを確認する。固定ルートを作成し、既存結果のためスキップするシナリオを除いた各Scenario IDについて、対象コミットからdetached HEADの一時worktreeを`$TMPDIR/agent-workflow-benchmark-full-run/<scenario-id>`へ作成する。
4. 同じプロジェクトで、会話履歴を引き継がない新規セッションを開始する。会話の圧縮、要約後の継続、既存会話の分岐は新規セッションとして扱わない。
5. 実行モードに対応する「固定の計測報告契約」とシナリオファイルの本文だけを変更せずに貼り付ける。ファイルパスを渡して作業Agent自身に読み込ませない。
6. 本書、結果テンプレート、過去の実行結果、シナリオの作成過程、関連コードを事前調査した会話を作業Agentへ渡さない。
7. 作業Agentの回答が完了するまで、計測や評価を目的とする追加指示を送らない。
8. 完了後に会話、ツール呼び出し、表示された出力を保存し、計測者が別途結果テンプレートへ転記・分類する。
9. `full-run`の場合は、各隔離worktreeの状態と差分を対応する結果へ記録し、全結果ファイルの検査とステージングが完了した後に、今回作成したScenario ID別worktreeであることを再確認して個別に後片付けする。固定ルートは今回作成した空ディレクトリである場合だけ削除する。

- シナリオの内容、関連コード、想定ルーティング、評価観点のいずれかをすでに確認したセッションは、コンテキストが混入しているため計測に再利用しない。
- 手順確認を目的とする試運転では未コミットの作業ツリーを使用してよいが、作業ツリーの状態を必ず記録する。
- 正式な基準値では、ベンチマーク定義を含む対象コミットを確定し、クリーンな作業ツリーから実行する。

## 計測区間

固定出力契約との互換性を維持するため、区間IDは英語表記のまま使用する。

| 区間ID | 開始 | 終了 |
|---|---|---|
| `initial_context` | 新規セッションを開始した時点 | 依頼の初回解釈を開始する直前 |
| `flow_selection` | 依頼の分類を開始した時点 | 対象領域、仕様影響、適用フローを確定した時点 |
| `document_loading` | 規約、仕様、ガイドの探索開始 | コード探索または成果物検討へ移る時点 |
| `code_exploration` | 対象コードの探索開始 | 調査結果または変更候補を確定した時点 |
| `deliverable_planning` | 着手前成果物の作成開始 | 調査回答、仕様案、または決定済み作業計画を完成した時点 |
| `implementation` | ファイル変更開始 | 初回の変更完了時点 |
| `review` | 自己レビューまたは専門レビュー開始 | 指摘反映の完了時点 |
| `verification` | 検証開始 | 最終結果の確定時点 |

- `pre-work`では`implementation`、`review`、`verification`を`not_applicable`とし、着手後に予定するスキル、レビュー、検証を別途記録する。
- コード調査のように`deliverable_planning`を分離できない場合も省略せず、`not_applicable`と理由を結果へ記録する。
- 実行中に区間を厳密に分離できない場合は、最も主要な目的に対応する区間へ記録し、判断理由を残す。

## コンテキスト取得イベント
- 作業Agentへ新しいテキストが渡った単位を、コンテキスト取得イベントとして記録する。
- 自動適用された`AGENTS.md`、固定入力、読み込んだ文書・コード、検索結果、コマンド出力を対象とする。
- 1回の出力に複数ファイルが含まれる場合は、取得量を分離できる範囲でファイルごとのイベントに分ける。分離不能な場合は取得元を`tool-output`として記録する。
- 取得行数は元ファイル全体ではなく、作業Agentへ実際に表示された行数を記録する。
- 同じファイルでも異なる範囲から新しい情報を取得した場合は別イベントとする。
- システム指示など内容や使用量を取得できない初期コンテキストは、推測値を入れず`not_available`と理由を記録する。

## 分類基準

後続比較との互換性を維持するため、分類値は英語表記のまま使用する。各イベントは次のいずれか一つに分類する。

| 分類 | 判定基準 |
|---|---|
| `required` | 適用される指示で常に参照が必須、または依頼を正しく完了するため不可欠である。 |
| `conditional-required` | シナリオ固有の変更領域、リスク、仕様影響、調査結果によって必要になった。 |
| `unnecessary` | 最終判断、成果物、検証、必須ガードレールのいずれにも寄与しなかった。 |
| `duplicate` | 先行イベントと同じ、または実質的に同じ内容を、新しい判断理由なく再取得した。 |

- 最初の必要な参照は`required`または`conditional-required`とし、同じ内容の再取得だけを`duplicate`とする。
- 分類は作業終了後に固定入力、実際の成果物、対象コミット時点の適用規約を基に確定し、結果へ根拠を記録する。
- 一部だけ必要だった出力は、合理的に分割できる場合だけイベントを分割する。分割不能な場合は主要な利用目的で分類し、その制約を記録する。

## 指標
- 実トークンを取得できる場合は、取得元と対象範囲を明記して`actual`として記録する。
- 工程別または参照先別の実トークンを取得できない場合は、計測可能コンテキスト行数を`proxy`として使用する。
- 実トークンと代替指標を加算せず、別々の欄へ記録する。

```text
計測可能コンテキスト総行数 = 全コンテキスト取得イベントの取得行数の合計
必要コンテキスト行数 = required行数 + conditional-required行数
必要コンテキスト率 = 必要コンテキスト行数 / 計測可能コンテキスト総行数
重複探索回数 = duplicateに分類した取得イベント数
```

- 行数を取得できないイベントは行数集計から除外し、除外件数と理由を残す。
- 総量に加え、同一資料の重複探索回数、予定したレビュー数、実行したレビュー数、処理時間、ルーティング選択と根拠、完了条件の見落とし有無を記録する。
- 必須文書、必須レビュー、必須検証、正しい成果物のいずれかが欠落した実行は、使用量が少なくても品質維持に失敗したものとして扱う。
