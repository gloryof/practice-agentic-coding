# 設計方針見直しチェック

## 目的
- 設計方針の見直し時に、評価観点と判定出力を標準化する。
- 設計判断の妥当性を、運用性・可観測性・コスト・リスクの観点で再現可能にする。

## 適用条件
- サービス境界や責務分割の変更を伴う。
- 運用方針（デプロイ、ロールバック、障害対応）の変更を伴う。
- 可観測性方針（ログ、メトリクス、トレース、アラート）の変更を伴う。
- コスト構造や主要なコストドライバの変更を伴う。

## 必須レビュアー
- `server-architecture-reviewer` を必須とする。
- 以下は条件付きで追加する。
  - セキュリティ論点がある: `security-engineer-reviewer`
  - DB 論点がある: `dba-reviewer`
  - テスト戦略論点がある: `qa-test-reviewer`

## チェックカテゴリ
1. 境界/責務
- サービス境界と責務が明確で、運用時のオーナーシップが曖昧でないこと。

2. 変更容易性
- 将来の機能追加や仕様変更に対して、変更影響の局所化が可能であること。

3. 運用性
- デプロイ手順、ロールバック手順、障害時の一次切り分け手順が明示されていること。

4. 可観測性
- ログ、メトリクス、トレース、アラートで原因特定可能な状態を維持できること。

5. コスト妥当性
- 主要なコストドライバ（計算、保存、転送、監視）が把握され、増減理由が説明可能であること。

6. リスクと回復計画
- 想定リスクに対する回避策と、失敗時のロールバック/ロールフォワード計画があること。

## 判定出力契約
- 設計方針見直しの成果物には、以下を必須で含める。
  - `Findings`
  - `Decision`（Keep / Revise / Reject）
  - `Required Actions`
  - `Verification Plan`

## 完了条件
- 適用条件に該当する見直し依頼で本チェックが実行される。
- 必須レビュアーおよび条件付きレビュアーが適用される。
- 判定出力契約の4項目が満たされる。
- 未解決リスクがある場合、`task/todo/TEMPLATE.md` 準拠で `Status: Proposed` の TODO が起票される。
- 起票後にステータス遷移した TODO は配置ルールに従って移動する（`Deferred` は `task/todo/deferred`、`Done` / `Dropped` は `task/todo/done`）。
